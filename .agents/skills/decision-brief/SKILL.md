# 人话版现状与决策说明（Decision Brief）

## 为什么需要

技术报告给人看的是证据，用户要做的却是决策。两者混在一起时，读者被术语和证据细节淹没，
看不出「现在到底卡在哪、我需要决定什么、决定了会怎样」。本技能规定一段固定的收尾输出，
让决策成本与阅读成本都降到最低，并强制把「我的猜测」和「我验过的事实」分开——
猜测混进事实是本项目长任务里最贵的一类错误（已多次发生）。

## 硬性规则

1. **位置与标题固定**：技术报告正文之后另起一段，标题一律为
   `## 人话版：现状与要你拍板的决定`。不许省略，不许并入正文。
2. **顺序固定**（缺项写「无」，不跳序）：
   ① 一句话现状 → ② 一页进度总览表 → ③ 已确定的 / 还说不准的 → ④ 待决选项与各自后果 → ⑤ 我的推荐
3. **零未解释术语**：正文里的函数名、文件名、缩写、专有名词，人话版里要么换成日常用语，
   要么紧跟一句括号解释。查下面的「术语→人话」表；表里没有的词自己造日常说法，
   **不要把同一个术语原样搬进去**。自检：假定读者从没看过本报告，能否只看这段就明白。
4. **已定与未定绝不混列**。凡带「可能 / 应该 / 看起来 / 推测」的一律进「还说不准」，
   并配一句「用什么能一次性验掉」。**否定证据（「没找到 X」）不等于证明（「X 不存在」）**，
   这个区别必须写出来。
5. **仪器失灵不许当结论**：报出「0 命中 / 全通过 / 全失败」之前，必须先确认
   测的是对的对象、阈值与判据本身有效。本项目反复栽在这一条上（指针闸设错、
   校准只看值不看周边、结构闸把真指针全拒、断言键名笔误导致半年恒绿灯）。
   人话版里遇到这类结果，要直说「这个数字现在不可信，因为……」。
6. **判定翻盘必须显式公告**：上一版人话版里写进「卡在哪 / 未达标 / 未解决」的某条结论，
   若在同一轮或后续轮内被推翻（改判达标、或前提作废），重发的人话版必须：
   - 开头用一行 `**更正**` 写明「<N> 分钟前那条『<原句摘要>』已被推翻」；
   - **原句照抄保留**（引号或划掉），**不得静默改写**成「一直是这个结论」——
     用户可能已经按旧版做出选择（本项目实例：用户正是在「id 交集 0、验收未达标」那版上拍了 A、B，
     而同阶段稍后改判为「标量 138,669 对一致率 99.974% 达标」）；
   - 写清**翻盘判据**：哪条新测量/新证据把它顶掉的，以及旧结论是否已导致执行过的动作；
   - `PROJECT_STATUS.md` 里那行同样就地标注「（本行的 <旧结论> 已被 <新证据> 推翻，保留以免重犯）」，
     不要删掉重写——文档侧与聊天侧必须用同一种「留痕」方式。
7. **选项要能直接拍板**：每个写清「你要做什么 / 大约多久 / 失败退回哪里 / 可不可逆」。
   一次最多 3 个；**超过 3 个就说明还没想清楚**，必须自己先折叠成「1 个推荐 + 一句『其余不急，定了这个再说』」，
   不许直接列 4 个及以上（本项目漂移过一次：实际给了 A/B/C/D 四项）。
8. **涉及模拟器的选项必须标出「需要你动手」**（要用户把界面开到某个画面、点某处），
   否则用户无法判断成本。
9. **体量红线**：整段 ≤ 40 行；进度总览表 ≤ 6 行。
10. 本轮确实不需要用户决策时，写一行「**本轮没有需要你拍板的事**」，仍保留本段结构。
11. **选中即执行 = 一次新的阶段收尾**：用户以选项字母回复选中一个或多个选项
    （「A」「A、B」「先做 A」）时，执行完**不得只补一行进度**：技术报告之后仍要重发完整人话版
    （骨架 ①~⑤ 全项齐），首句点名「你选的 A（、B）已做完，结论是 <一句话>」；
    多选项时进度总览按选项分行。（2026-09-25 两轮已按此执行，此处固化为规则。）

## 骨架（直接抄用）

```markdown
## 人话版：现状与要你拍板的决定

**一句话现状**：<目标到哪一步、卡在哪、卡点是技术问题还是未知信息>

**更正**：<仅在上一版有判定被本轮推翻时保留：X 分钟前那条「<原句>」已被推翻，判据是 <新证据>>

| 进度总览 | |
|---|---|
| 目标 | <用户真正要的东西> |
| 已到手 | <可直接使用的产物或结论> |
| 卡在哪 | <一个具体障碍> |
| 还差 | <完成目标所需的最小未知量> |

**已经确定的**（有证据，可当事实用）
- <事实> —— 依据：<怎么测出来的>

**还说不准的**（我的推断，别当事实用）
- <猜测> —— 怎么验：<什么操作能一次定死它>

**要你拍板**
- **A 做 X**：需 <谁做什么>，约 <时长>，失败退回 <哪里>，<可逆/不可逆>
- **B 做 Y**：……

**我的推荐**：<A/B> —— <一行理由>
（不认可直说，我按你的判断走）
```

## 本项目术语 → 人话对照

写人话版时按右列措辞；括号里是给人的补充解释，可省则省。

| 报告里的术语 | 人话版怎么说 |
|---|---|
| `sharecfgdata/*` 配置表 | 游戏里存"表"的那批文件（舰船属性、台词索引、阵营码等） |
| `www()` / 流密码 / TEA 解密 | 游戏自己那套"把文件还原成能用数据"的解码函数 |
| AssetBundle / AB / `UnityFS` | Unity 的资源包格式（游戏素材的打包容器） |
| Lua 字节码 / chunk / `lua_loadbuffer` | 把"程序代码编译后的中间形式"交给脚本虚拟机去执行 |
| `LuaConfDataReader` / `ReadData(startPos,size)` | 游戏读配置表的入口，按需读文件中段的一小片 |
| 内存取证 / 快照 | 游戏运行时把它的内存内容抓下来看（需要模拟器开着你得配合操作） |
| 反汇编 / callee / `--xref` | 直接读程序编译后的机器指令；查"谁调用了它" |
| metadata `global-metadata.dat` / InitializeArray blob | 存"名字和常量"的元数据文件；那串内联常量要从里面抠 |
| trailer / footer / magic | 文件尾部字段 / 固定尾巴 / 文件开头的身份标识字节 |
| 假绿灯 | 看起来通过其实没验的检查（工具失灵造成的假成功） |
| 判据 | 用什么现象来判定"成功/失败"的标准 |
| 否证 / 证伪 | 证明"不是这样"，注意与"我没找到证据"区分 |
| PPtr / externals / CAB | 资源包内部的跨文件引用 |
| `moc3` / `model3.json` / HitAreas | Live2D 模型本体 / 模型清单 / 可点击判定区 |
| ACB / cue | 音频包 / 包里一条具名语音 |
| LEB128 / 记录流 | 一种紧凑数字编码 / 数据按小记录一条条排 |
| 基线重标定 | 老的标准数字作废，要用新标准重测一遍 |

## 常见失败模式

- **写成了技术报告的摘要**：仍然满是术语。判据：读者不需要背景知识就能回答「我要不要动手、动什么」。
- **进度总览写成待办清单**：总览是「现在在哪」，不是「接下来做几件事」。
- **只给选项不给后果**：没有代价与可逆性的选项等于没给选项。
- **把猜测写进「已确定」**：最危险，会让用户据此做不可逆决定。
- **把工具的空结果讲成发现**：本项目已有多次「0 命中其实是探针坏了」。
- **把翻盘静默改写**：上一版说「卡在哪 = X 未达标」，本版直接写成「已达标」，看起来一直是对的。
  用户可能已经按旧版拍板（本项目实例：用户正是在「id 交集 0」那版上选了 A、B）。必须走规则 6 的留痕格式。
- **执行完选中选项只回一行进度**：用户失去了再次拍板的入口——选完 A 之后，A 的结果就是下一轮的现状。
- **选项超过 3 个**：把决策负担推回给用户。超过 3 个是信号：你自己还没排出优先级。

## 与其他约定的配合

- 本项目「阶段收尾必做清单」（文档同步、探针处置、提交、确认行）照走；
  人话版放在**全部技术收尾动作之后**，作为最后一屏。它的任务不是汇报工作量，
  而是让用户能决定下一步。
- 长任务（批量、后台、取证）中途被打断回答提问时，也应先给三行版本：
  现状 / 卡点 / 要不要你现在决定什么。
- 若结论会影响 `PROJECT_STATUS.md` 的状态 emoji，人话版里那句"已确定/未定"必须与之对应：
  ⚠️ 与 ⏳ 的项不许出现在「已经确定的」里。
