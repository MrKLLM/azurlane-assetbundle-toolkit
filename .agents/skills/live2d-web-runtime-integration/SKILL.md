# Live2D 网页运行时集成

## Overview

把 Cubism 4 的 `.model3.json` 模型在浏览器里渲染成可交互、会播动作的 Live2D。核心难点不在"加载出来"，而在**动作真的在播**、**点击部位触发对应反应**、**构图不越界**——这三处各有一个会静默失败的陷阱。

## 适用判断

- 页面里已有/可放 `live2dcubismcore.min.js` 等运行时，要让模型动起来 → 用本流程
- 只是把模型贴图当静态图展示 → 不需要运行时，直接 `<img src="texture_00.png">`
- 要产出的不是"网页里的模型"而是从游戏包还原模型文件本身 → 先走 `unity-assetbundle-painting-restore`

## 1. 运行时三件套与版本组合

必须**按序**加载，且版本要成对（新 pixi 会破坏 display 适配层）：

1. `live2dcubismcore.min.js`（Cubism Core，实测 5.1.0）
2. `pixi.min.js`（实测 **6.5.2**）
3. `pixi-live2d-display-cubism4.min.js`（实测 **0.4.0**）

- **别用 pixi 7 / display 0.5**：本项目实测 pixi 6.5.2 + display 0.4.0 是可用组合。
- 国内网络：`live2dcubismcore.min.js` 可从 l2d 系站点直链取；pixi 与 display 走 npmmirror 的 **tgz 下载后解包取 `dist/`**（registry 元数据接口可能被拦）。下载细节见 `cn-blocked-resource-mirror-fetch`。
- 全部放本地 `vendor/live2d/`，**别用 `P`（资源相对路径前缀）拼 vendor**：若 vendor 与页面同目录，用 `./vendor/live2d/…`。判定办法是在页面里 `fetch('../vendor/…')` 与 `fetch('/<页面目录>/vendor/…')` 对比状态码，**别信 curl 的绝对路径**（curl 的 200 会掩盖相对路径错误）。
- 懒加载（点标签才加载）比顶部 `<script>` 好：用 `loadScriptOnce(src)`（按 `script[data-x]` 去重并缓存 Promise），避免首屏拖慢与重复注入。

## 2. 加载模型

```js
const mdl = await PIXI.live2d.Live2DModel.from('<dir>/<name>.model3.json', { autoInteract: false });
app.stage.addChild(mdl);
```

- `autoInteract: false` 时库自带的 hit test/视线跟随都关掉，交互自己实现（见 §4）。
- 需要 `FileReferences.Motions` 的组名列表：`mdl.internalModel.motionManager.definitions`（键即组名）。

## 3. 动作播放：八个必踩陷阱（3.1–3.8）

### 3.1 `startMotion` 的 index 不能传 `null`

```js
mm.startMotion(group, null, false)   // ✗ 静默失败，什么都不播
mm.startMotion(group, 0, MP.FORCE)   // ✓
```

库内部会取 `motion[group][index]`；传 `null` 得到 `undefined` 后**直接 return false，不报错**。`priority` 也不能传 `false`——会被当成 0，低于当前优先级同样被拒。用 `PIXI.live2d.MotionPriority.FORCE`（枚举 NONE/IDLE/NORMAL/FORCE = 0/1/2/3）。

### 3.2 判"有没有在播"要读运行时状态，且要等一拍

`startMotion` 内部要 `fetch` 动作 JSON，调用后立刻读会拿到空值：

```js
mm.startMotion(g, 0, MP.FORCE);
await new Promise(r => setTimeout(r, 1500));
const playing = mm.state.currentGroup === g;   // 唯一可靠判据
```

**帧哈希/drawImage 比对不能当判据**：无头环境 rAF 被节流会**假阴性**；而 physics 与眨眼会让画面逐帧变化，造成"动作在播"的**假阳性**。另外注意：idle 播完后 `state.currentGroup` 会**自动归 null**，所以"值变了"才说明有东西被触发。

### 3.3 `Meta.Loop` 被忽略 → 但**不要**用前端定时器假装循环

vendored 0.4.0 的 cubism4 模块里 `setIsLoop()` **有定义、全 bundle 无调用点**，`Meta.Loop:true` 被无视，
动作播完即停。用定时器"到点重开"是**陷阱**：`startMotion` 是 async（返回 Promise），
`mm.startMotion(...) !== false` **恒成立**，于是被 `state.reserve()` 以
`"Motion is already playing"` 拒绝时前端完全无感，而重开定时器又照原周期重新武装 →
实测 idle 播 9.1s 后**冻结 9.2s**（`currentGroup=null`、队列 0 条、参数纹丝不动），50% 占空比。

正确修法（三行，交回运行时）：
```js
// ① 把 Meta.Loop 灌进 CubismMotion 本体（核心会自己做时间回绕：f>duration 就减 duration）
const orig = mm.createMotion.bind(mm);
mm.createMotion = (json, group, def) => { const m = orig(json, group, def);
  if (group === idleGroup && json?.Meta?.Loop && m.setIsLoop) {
    m.setIsLoop(true); m.setIsLoopFadeIn?.(false); }   // ← 后者必须设！
  return m; };
// ② 对齐库自带的"播完自动回 idle"：默认值是 'Idle'，与我们的 'idle' 不匹配 → 一直静默失效
mm.groups.idle = idleGroup;
```
⚠️ **`setIsLoopFadeIn(false)` 不能漏**：否则每次回绕都会 `setFadeInStartTime(now)`，
淡入权重每循环归零重爬一遍，观感 = "每隔 N 秒身子被拽回去"。
设了 ①② 之后**前端不需要任何动作计时器**，回落 idle 由库逐帧接管。

### 3.4 `_startMotion` 里的 `stopAllMotions()` 让动作切换**完全没有交叉淡化**

库的 cubism4 管理器每次起动作都先 `queueManager.stopAllMotions()` → 旧动作被瞬间掐死，
姿态硬跳（观感 = "动作不对、身子拧着、穿模"）。而队列管理器自己的 `startMotion`
**本来就会给现存条目 `setFadeOut()`** —— 所以只要不再调 stop 就恢复官方交叉淡化：
```js
mm._startMotion = (m, onFinished) => { try{ m.setFinishedMotionHandler(onFinished); }catch(e){}
  return mm.queueManager.startMotion(m, false, performance.now()); };
```
配合 3.3 的循环动作要注意：`_isLoop=true` 时 `getDuration()` 返回 −1 → `endTime=-1` →
淡出权重恒 1；但条目被 `setFadeOut` 触发淡出时 `startFadeOut` 会把 `endTime<0` 改成
`now+fadeOut`，所以**循环动作仍能正常淡出退场**，不会赖着不走。

### 3.5 运行时自加的 Cubism2 式「呼吸层」——Cubism4 模型必须关掉

`Cubism4InternalModel` **无条件**挂 `CubismBreath`，每帧在动作**之后**再 ADD 五个参数：
`ParamAngleX ±7.5°@6.5s / Y ±4°@3.5s / Z ±5°@5.5s / ParamBodyAngleX ±2°@15.5s / ParamBreath ±0.25@3.2s`。
而 Cubism4 模型的动作**本来就自带**这些参数的动画（碧蓝全库 74~85% 的 idle 有）→ **头部双驱动**，
观感 = "一直在有点快地动、不自然"。铁证：游戏侧 bundle 的 MonoBehaviour 组件清单
（`CubismMoc/Model/Parameter/PhysicsController/Raycaster/MouthController/Live2dChar`）里**根本没有 Breath**。
```js
internalModel.breath?.setParameters([]);   // 关掉，播放完全等于动作数据本身
```
（`updateFocus()` 也是每帧 ADD，但 `autoInteract:false` 时 focusController 恒为 0，无害。）

### 3.6 判定区/淡入淡出/Groups 别自己拍脑袋，跟权威实现对齐

model3.json 里三处最容易自以为是：
- **淡入淡出**：给每条动作硬写 `FadeInTime/FadeOutTime:0.5` 会让"回落 idle"比运行时默认
  （idle 组 **2s**、其余 0.5s）快 4 倍 → 反应没收尾就被拽回去。**不写**才交给运行时默认。
  若 idle 带大量定值曲线，2s 淡出会在点击后继续拖尾 2 秒把参数往回拽 → 显式拆开
  `FadeInTime:2.0, FadeOutTime:0.5`（库里这两值默认共用同一个 idle 常量，只能显式覆盖）。
- **`Groups`** 缺 `EyeBlink`/`LipSync` 时 `internalModel.eyeBlink` 直接是 undefined（模型不眨眼）。
- **`HitAreas` 不止 Head/Body/Special**：moc3 里可能有几十个 `Touch*` 标记（碧蓝安土有 76 个：
  `TouchDrag1-24`、`TouchIdle1-47`）。只登记三个 → 点其它区域毫无反应。
  补登时务必实测**新框与核心框是否重叠**（安土实测零重叠才敢上）。

### 3.7 销毁与泄漏

`app.destroy(true,{children:true,baseTexture:true,texture:true})` 不会移除 `window` 级监听。把所有监听存进状态对象并提供 `off()`，切换标签/关闭弹窗时统一调用：

```js
state.off = () => { ro.disconnect(); wrap.removeEventListener(...); window.removeEventListener('pointermove', onMove); ... };
```

### 3.8 clip 驱动过的参数无人回写 → 模型整体移位、判定区全丢（"进去就出不来"）

**症状**：某个动作（安土 `touch_idle1`）播完之后判定区集体失效。实测画布 20×16 模型单位，静止态 57 个判定区已有 53 个在画布外（只有核心 3 个 + `touch_idle1` 真可点）；播完这条 clip 后 **57 个全部出画**，核心三个一起被甩到同一点 `(-36.37,-52.81)`，回到 idle 也不恢复。
> ⚠️ **别把"静止态出画"当成脏数据**（2026-09-27 实测否证过一次误判）：那些出画的 `TouchIdle*/TouchDrag*`
> 往往是**换装/互动按钮的停放位**——它们挂在会动的道具上，播对应动作时才随部件进画面。
> 判别方法：逐动作组播一遍、每组重新量"有几个标记落回画布内"（本项目 `l2d_hit_offcanvas.py --sweep`）；
> 静止态 4/26 → 播某些组时 7~10 个，即证明是动画驱动，**不可按几何位置批量删除**。
> 换装状态的落地形态是「各 clip 用定值曲线锁住 `TouchSiwa`/`Paramaixin` 这类开关参数」，
> 所以按钮的 `HitAreas[].Name` 就是那条动作组名，与"随机取同组另一条"的命中规则天然兼容。

**根因**：Cubism 只对"本 clip 有曲线的"参数施权，**缺曲线的参数停在上一个动作留下的值上**。该 clip 252 条曲线里 **15 条 `idle` 从不驱动**（含整体位移）→ clip 末帧值永久残留。游戏侧靠 `change_in`/`home` 状态机复位，Web 运行时没有状态机，所以同一份数据在游戏里不暴露。（导出侧同一条机制见 §6.5「`m_ConstantClip` 定值曲线不是惰性的」。）

**定位 = 参数集求差，不靠猜**：对 motion3.json 取 `{c.Id | c.Target=="Parameter"}`，算 `clip集 − idle集`。
⚠️ `Id` 有两种形态，纯字符串 或 `{string:"ParamX"}`，判据要兜两种：
```js
const curveId = c => typeof c.Id === 'string' ? c.Id : (c.Id && c.Id.string) || null;
```
差集非空即锁定嫌疑人。

**修法**：复用 §3.3 那个 `createMotion` 补丁顺手登记每组参数集（零额外请求），`play()` 里 `if (g !== idleGroup) played.add(g)`，再用一个 ticker 回写：

```js
const restTick = () => { const cg = mm.state?.currentGroup;
  if (cg && cg !== idleGroup) { rest = null; return; }               // ② 只在回 idle/队列空时才动
  if (!rest) { const idleS = paramSets[idleGroup]; if (!idleS || !played.size) return;
    const want = new Set();                                          // ① 只碰播过的 clip 驱动过的参数
    played.forEach(g => (paramSets[g] || new Set()).forEach(p => { if (!idleS.has(p)) want.add(p); }));
    played.clear(); const items = [];
    want.forEach(p => { let i = -1; try { i = cm.getParameterIndex(p); } catch (e) {}
      if (i >= 0) try { items.push([i, cm.getParameterValueByIndex(i), cm.getParameterDefaultValue(i)]); } catch (e) {} });
    if (!items.length) return;
    rest = { items, t0: performance.now() + REST_DELAY }; return; }  // ③ 先等上一条淡出跑完
  const el = performance.now() - rest.t0; if (el < 0) return;
  const k = Math.min(1, el / REST_MS);
  for (const it of rest.items) try { cm.setParameterValueByIndex(it[0], it[1] + (it[2] - it[1]) * k); } catch (e) {}
  if (k >= 1) rest = null; };
app.ticker.add(restTick);   // REST_DELAY=400, REST_MS=700
```

三道防误伤约束：① 只处理「播过的 clip 驱动、idle 不驱动」的参数，物理/眨眼/口型等 clip 无关参数一律不动；
② 只在回到 idle（或队列空）时触发；③ 先等 `REST_DELAY` 让淡出跑完，再线性渐变过去（硬赋值会跳帧）。
目标值取 **moc3 默认值**（`getParameterDefaultValue`）而非"进动作前的快照"：这些参数在静止态本就没人动，
默认值 ≡ 静止位，且与快照时机无关。

**坑：`paramSets[idleGroup]` 为空 ⇒ 复位永远不触发**（那个 `if (!idleS) return` 是静默的）。
当 idle 的 motion 在补丁挂上**之前**就被创建时发生——库的预加载分支是
`switch (config.motionPreload) { default: e = [this.groups.idle] }`，所以 `motionPreload:'ALL'`
或组名恰为库默认的 `Idle` 时必踩。本项目组名是小写 `idle` 而 `mm.groups.idle` 要到 §3.3 的补丁里才被改成小写，
默认路径不预加载、侥幸躲过——但**判据必须显式断言 `paramSets[idleGroup]?.size > 0`**。
兜底做法：另 fetch 一次 idle 各条 json 登记参数集，顺带补 `Meta.Loop`（同一份 json，别开第二条管线）。

## 4. 按部位点击触发（HitAreas）

游戏里的 Live2D 是**点击部位**触发（不是悬停）。数据在 `model3.json` 顶层 `HitAreas`：

```json
[{"Id":"TouchHead","Name":"Head"}, {"Id":"TouchBody","Name":"Body"}, {"Id":"TouchSpecial","Name":"Special"}]
```

- **`HitAreas[].Name` 通常就是动作组名**（本项目 256 模型 768 个判定区对 `FileReferences.Motions` 键 **768/768 精确匹配**）。先跑一次全库统计验证这个假设，别凭直觉找 `tap*` 组——多数模型根本没有裸 `tap` 组，于是"点哪儿都不动"。
- 取判定几何：`idx = coreModel.getDrawableIndex(a.Id)`，再 `coreModel.getDrawableVertexPositions(idx)`（模型单位，x/y 交替）。**点击瞬间实时读，不要缓存**——框会随呼吸/物理每帧位移，缓存坐标会点空。
- 坐标换算：`const lp = mdl.toLocal(new PIXI.Point(屏幕x - wrapRect.left, 屏幕y - wrapRect.top)); const 单位 = lp.x / internalModel.pixelsPerUnit`。
- **判定形状 = 部件的真实四边形（两三角），不是它的轴对齐包围盒**（2026-09-23 二次修订，推翻本条旧结论）。
  游戏侧 `CubismRaycaster` 就是对 `Touch*` 部件做三角形 raycast。这些标记是 4 顶点不可见 quad，
  **部分模型的 quad 是斜的**：四边形面积/包围盒面积比 = `yingrui_3` 0.489~0.755、`z46_3` 0.645~0.942，
  用包围盒等于把判定区放大最多 2 倍 → 点旁边空地也触发（用户报"有些点击不准"）。
  正矩形模型（碧蓝安土 `antu_2` 等，比值 1.000）两种判定**逐点等价**，零行为变化。
  ⚠️ **本条旧结论"三角面反而更差、包围盒 767/768"是错的**：那次实测是在**坐标系换算还没修对**时做的，
  且试图用 `coreModel.getDrawableIndices()` —— **该方法在 live2dcubismcore 的 Model 包装上根本不存在**
  （只有 `core.drawables.indices[i]`），拿到 undefined 后判定全崩，被误当成"三角面数据不规整"。
  正确做法：4 顶点按**三角带序**拆成 `(v0,v1,v2)+(v1,v3,v2)`，无需索引缓冲；实测 5 个模型
  `带序面积 == 凸包面积`，证明带序假设成立。包围盒只当**快速预筛**用。
- **顶点序是三角带，画多边形必须换环序**：`getDrawableVertexPositions` 给的是 `(TR,TL,BR,BL)` 带序，
  直接 `drawPolygon(v0,v1,v2,v3)` 会连成**自交蝴蝶结**。无自交环序是 `[0,1,3,2]`。
- 多个框同时包含时（部位框常重叠/嵌套）取**面积最小的框**（最具体的部位优先）。
  旧的"归一化中心距离就近取"在嵌套框上会选到大框；改最小面积后安土等正矩形模型行为不变，
  `yingrui_3`/`z46_3` 的斜框误伤被剔掉（实测收窄 26.4%）。
- 容差只给 **2%**（吸收测试派发延迟的几十毫秒位移）。给到 8% 会把视觉上明显空白的角落判成命中——Live2D 画布四周有大量透明边距，模型单位范围比可见内容大得多。
- **兜底动作只给没有 `HitAreas` 的模型**。有判定区却点框外，就什么都不播（与游戏一致）。否则点哪儿都蹦一个 `touch_drag*`，观感极差。前端配套：`fallbackG = hitAreas.length ? null : <兜底组>`——`hitAreas` 非空时把兜底组设为 `null`，才会出现"点框外不播"；否则形同空壳。

## 4.5 生成真实 HitAreas（修补占位 Id，2026-09-22 碧蓝航线实测）

§4 讲的是**消费**已有 HitAreas；本节讲**如何为占位模型批量生成正确 HitAreas**（`fix_model3.py` 一类管线）。典型根因：还原管线早期只往 `model3.json` 补占位 Id `HitArea/HitArea2`，而前端 `getDrawableIndex("HitArea")` 取不到 drawable → 判定区被过滤成空 → 点部位退化成兜底乱播。

- **保守只替换占位 Id**：仅当某模型现有 `HitAreas[].Id ⊆ {HitArea, HitArea2}` 时才改写；已带正确 Id 的模型**一律不动**。这样"256 个既有模型零回退"是**构造性保证**（压根不进改写分支），不靠事后校验兜底。
- **`Id`**：碧蓝统一用 `TouchHead/TouchBody/TouchSpecial`，须能被 `getDrawableIndex(a.Id)` 解析（返回值 `≥0`）。**改写前先逐字节探针确认该 drawable 真的在 moc3 里**——判据是 `getDrawableIndex("TouchHead") >= 0` **且** `getDrawableVertexPositions(idx)` 非空（如 4 点 = `vlen=8`）。只有**部件名**（Part）不算，必须是**drawable**，否则前端仍取不到框。
- **`Name`**：必须是**该模型真实存在的动作组**，即能在 `FileReferences.Motions` 的键里找到。按候选顺序取第一个命中的（小写回落，兼容不同命名世代）：
  - `Head → [Head, head, tapHead, taphead, tap_head, touch_head, TapHead]`
  - `Body → [Body, body, tapBody, tapbody, tap_body, touch_body, TapBody]`
  - `Special → [Special, special, tapSpecial, tapspecial, tap_special, touch_special, TapSpecial]`
  经验：老模型组名是 `Head/Body/Special`，新换入模型是 `touch_head/touch_body/touch_special`——两代都要覆盖，只认其一就是"点哪儿都不动"的来源。
- **改后必须证"仅该字段变"**：跑前对全部 `model3.json` 快照 `(path, mtime, sha256)` 清单，跑 `fix_model3` 后 diff → 断言"**仅 N 个文件变、且每个文件仅 `HitAreas` 字段变**"（顶层键集合不变、`changed_fields == ['HitAreas']`）。任何其它字段被顺带改动 = 回退，立即排查。
- **收尾**：`hit_verify --only <这批 key>` 逐个证 **3/3 命中**（点击各 drawable 框中心 → `state.currentGroup == HitAreas[].Name`）；再全库复跑确认命中数增量 == 新启用的判定区数（本项目 13 模型 × 3 = +39，768→807、767→806，同一 `z46_3` 嵌套框歧义为既有非回退项）。
- **⚠️ 静止态落在画布外的 `Touch*` 不等于脏数据，不许按几何位置批量过滤或删除**。这类标记常挂在**会动的道具**上（按钮/绳索/手持物），静止态被停在画布外几千像素处，播对应动作时才随部件进画面才可点。判别式只有一个：**逐动作组播一遍（走页面自己的 `play()`，别直接 `startMotion`），每组重新量"落回画布内"的标记数**——静止态 4/26、播某些组时 7~10 个即证明是动画驱动。
- **换装/开关类交互的落地形态是"各 clip 用定值曲线锁住开关参数"**（如 `TouchSiwa`/`Paramaixin` 这类 Parameter，`touch_idle31` 里 `Paramaixin=1.6` 就是爱心眼）。所以按钮的 `HitAreas[].Name` 本来就是那条动作组名，**不需要另造切换机制**；反过来，一个 `Touch<X>` 若没有同名动作组，多半是"开关参数 + 停放标记"，而不是可点部位。

## 5. 构图与 fit 的两个陷阱

1. **别用 `mdl.width` 当模型尺寸**：pixi-live2d-display 下它可能返回 1 或被污染的包围盒（个别模型被巨型离屏 quad 撑到百万像素）。可靠基准是 `internalModel.width / internalModel.height`（= Cubism 画布单位 × `pixelsPerUnit`，如 8000×8000）。
2. **`fit()` 必须幂等**：`DisplayObject.width` 已含 `scale`。若在 fit 里用 `mdl.width` 算缩放，`ResizeObserver` 二次触发时会**正反馈放大**，画面糊成局部特写。做法：加载后缓存未缩放尺寸（或直接用 `internalModel.width`），维护 `baseK(适配) × z(用户缩放)` 与偏移 `ox/oy`，`apply()` 统一由这三者算 scale 与位置；`fit()` 只是把 `z/ox/oy` 归零后 `apply()`。

## 6. 交互层反模式

- **不要 `preventDefault` 劫持裸滚轮**。鼠标经过模型时用户可能正在滚页面，被劫持后页面不动、模型一路放大并累积平移，看起来像"模型自己乱动、位置不对"。改成 **Ctrl/⌘/Alt + 滚轮**才缩放，并在提示文案里写明。
- 拖拽必须处理 `pointercancel` 与 `window blur`，否则拖拽态卡住，之后每次鼠标移动都在平移模型。
- 平移量要钳制（如 `max(wrapW,wrapH)*0.6`），防止把模型拖出视野再也找不回。
- 位移 < 6px 视为"点击"而非"拖拽"，用来触发动作。

## 6.5 motion 数据从哪来：Unity AnimationClip → motion3.json 的权威映射

（从 Unity AssetBundle 侧还原动作时的正确姿势，2026-09-21 碧蓝航线实测）

- **curve index ↔ `m_ClipBindingConstant.genericBindings[i]` 同序**；且
  `genericBindings[i].path = crc32("Parameters/<GameObject名>")`，部件是 `crc32("Parts/"+名)`。
  实测 946274 个绑定的解析率 99.77%（未解析的 0.226% 是第三类属性哈希，运行时无对应 motion target，只能跳过）。
  不是 sdbm/djb2/FNV——别再试别的哈希函数。
- `CubismParameter` 组件的 `m_Name` 是**空**的：真名挂在 **GameObject** 上，`_unmanagedIndex` 才是
  moc3 参数序号。被动画化的序号是**稀疏**的（实测 `lingbo/idle` = 0,1,2,8,9,12,13,14,15,18,…），
  所以**绝不能假设 "curve idx == 参数序号（从 0 连续）"**——这是"眼睛数据写进眉毛参数"的来源，
  模型会照常动，只是动得面目全非（乱飘/乱闪/个别没反应）。按组件枚举顺序取参数名同样是错的。
- StreamedClip 的**帧 0 是 `time=-3.4e38` 的参考姿态帧，一帧合法写完全部曲线**（大模型一帧 380~520 个 key）。
  任何 `if numKeys > N: break` 之类的"合理性护栏"都会在帧 0 崩掉整条动作；
  只能靠 `+inf` 结束符 + 缓冲区边界停。该帧要当作各曲线 t=0 的基准值，而不是当普通关键帧丢掉。
- **⚠️⚠️ 贝塞尔控制点是「绝对 (时间, 值)」，不是归一化分数**（2026-09-23 血泪根因）。
  段序仍是 `[1, c1x, c1y, c2x, c2y, 终点time, 终点value]`（终点在最后，官方没有第 5 个
  "interpolation" 字段），但运行时解析器是**直读不做任何还原**：
  ```js
  case Bezier:
    points[a]   = new j(seg[l+1], seg[l+2])   // (时间, 值) —— 绝对坐标
    points[a+1] = new j(seg[l+3], seg[l+4])
    points[a+2] = new j(seg[l+5], seg[l+6])
  ```
  若按归一化写 `[1, 1/3, by1, 2/3, by2, t, v]`，控制点会被读成「t=0.333 **秒**、值=0.667」——
  落在段外且值接近 0 → **每条贝塞尔都先猛蹿到≈0 再跳到目标值**。表现为"部件各动各的、
  像刚学建模的人做的、穿模"，而**曲线数/时长/参数名/量程全部校验都能通过**，极难自察。
  正确写法 = Unity 三次 Hermite 的等价控制多边形：
  `c1=(t0+dt/3, v0+outSlope·dt/3)`、`c2=(t1−dt/3, v1−inSlope·dt/3)`。
- **但"格式正确"≠"效果正确"**：Unity **密集键**（相邻键 ≪ 周期）的那对切线字段本就不该当 Hermite
  切线用，照上面算会飞出几百个参数单位。碧蓝实测三种写法对权威基准的逐曲线偏差（121 点采样）：
  | 写法 | 偏差中位 | 偏差>0.5 的曲线 | 最甚 |
  |---|---|---|---|
  | 归一化控制点 | 1.376 | 92/98 | 9.35 |
  | 绝对控制点·全贝塞尔 | 0 | 88/278 | **296** |
  | **关键帧 + 线性**（采用） | 0 | 11/278 | 1.95 |
  → 从 Unity AnimationClip 反解时，**默认就该发线性段**；`|dv|<1e-3·max(1,|v0|,|v1|)` 的退化线性
  与 `|by|>3` 拉直都是掩盖格式错误的权宜，别当成优化保留。
- **`Meta` 要对齐**：`Fps` 取 `AnimationClip.m_SampleRate`（别硬编码 30）；`AreBeziersRestricted:true`
  的含义是"控制点横向恒在 1/3、2/3"→ 运行时走朴素参数化求值（不解三次方程），与上面的发法自洽。
- **⚠️ Unity 曲线分装在三个容器，只读 `m_StreamedClip` 会丢数据**：
  `m_Clip.data` 有 `m_StreamedClip` / `m_DenseClip` / `m_ConstantClip`，
  而 `genericBindings` 的顺序 = **[streamed][dense][constant]**（实测 98+0+180=278 且名字零冲突）。
  `m_ConstantClip` 是"整段保持定值"的曲线，**不是惰性的**：Cubism 只对"本 clip 有曲线的"参数施权，
  缺曲线的参数在切动作时**停在上一个动作留下的值上** → 被 `touch_*` 动过的手臂回不到静止位 → 部件错位。
  参考实现的 `idle` 曲线数正是 streamed+constant 之和。**务必一并导出定值曲线**
  （`Segments:[0, v, 0, duration, v]`，每条 1 段 2 点）。
- 运行时**完全不读 `pose3.json` / model3 的 `Pose` 键**（该字符串在 pixi-live2d-display 里出现 0 次），
  但支持 motion3 的 `Target:"PartOpacity"` → 换装/部件可见性只能写进 motion3.json，出 pose3 是死路。

### 6.6 `Textures` 清单是**按索引**消费的：枚举序必须显式归一 + 闸门 + 看图

`model3.json` 的 `FileReferences.Textures` 数组，运行时把第 i 项绑给 moc3 的**纹理索引 i**。
moc3 文件里**不含任何贴图名**（碧蓝 269 个 moc3 全量搜不到 `texture_*.png` 字符串），
所以"哪张图是索引 0"这件事**只能由清单顺序决定**，错了不会报错、只会画面碎。

- **典型症状**：模型加载成功、动作在播、参数在动，但画面是"几十个部件碎片叠一堆"
  ——每个 art mesh 从别的图集里采样。背景层（往往集中在某一张图）看起来还大体成形，
  这反而最容易骗人："渲染出东西了"被当成"渲染对了"。
- **导出侧的坑**：从 Unity bundle 落贴图时用的是序列化对象的**枚举顺序**，
  它 ≠ 索引顺序。碧蓝实测 **51/269 个模型两者不一致**（最狠的一个 6 张图枚举成 `[02,05,00,03,04,01]`）。
  也就是说这一步**必须在写完后显式归一**，不能指望生产方的迭代顺序；
  归一化是承重步骤，不是装饰。
- **归一规则**：按名中数字排（`texture_%02d` 的编号即索引），无数字者排在带数字之后按名称序。
  前提是先全量确认命名齐整（碧蓝：`非 texture_%02d 命名 = 0`），否则"编号即索引"这条约定不成立。
- **闸门**（退出码即判据，只读检查、`--apply` 才写）：`l2d_texorder_check.py`。
- **完整性对账**（另一类静默失败：解码 `except: continue` 悄悄少一张，结构仍合法）：
  逐模型比 源 bundle 的 `Texture2D` 清单 vs 磁盘 PNG，报 `missing / extra / 命名异常`。
- **⚠️ 验收必须包含"逐张看图"**：加载成功、`getDrawableCount()`、参数跨帧 min/max、帧哈希在变——
  在错绑这一类故障下**全部为真**。代理指标只能证"没死"，不能证"对"。
  看图工具要现成（否则它自然被代理指标顶替），且**判据要写明"和什么比"**：
  本技能实测把一张"人躺在地上、腿朝镜头"的正常前缩透视误判过一次"姿势反常"，
  拿同皮肤的静态立绘一比即证伪。可比对象优先级：同皮肤静态立绘 > 同批未改动对照组 > 权威外部实现。

## 7. 无头验证判据（配合 CDP）

### 7.0 自研管线必须找**外部权威实现**做基准，自证清白一定会漏

**教训**：碧蓝 Live2D 的 motion3.json 控制点格式错了整整一个量级（见 §6.5），但
曲线数、时长、参数名映射、量程、空壳率**全部校验通过**，`hit_verify` 也是 806/807 全绿——
因为这些都只验证"结构自洽"，不验证"和原作一样"。用户反馈"部件各动各的、像刚学建模的人做的"
持续了好几轮，我先后误判成呼吸层、误判成插值护栏，**直到拿到同模型的权威导出才一次锁定**。

可用的外部基准（同一批游戏模型、成熟 Cubism 实现）：
```
https://static.l2d.su/azurlane/live2d/<key>/<key>.model3.json
https://static.l2d.su/azurlane/live2d/<key>/motions/<组>.motion3.json   # 注意 motions/ 复数
```
路径规律是从它的 SPA bundle（`/assets/index-*.js`）里 grep `model3.json` 模板反查出来的；
只覆盖部分模型（抽样 8/14），404 就跳过。比对**逐曲线按运行时真实语义采样求值**
（linear 插值 / stepped 取起点 / bezier 在 `AreBeziersRestricted` 下用归一化时间直接当贝塞尔参数），
判据：组与曲线集合零缺失、**关键帧零不一致**、偏差中位 ≤0.5、偏差>0.5 占比 ≤12%
（12% 是按"结构完全正确时的真实残差"校准的，不是拍脑袋）。

**没有外部基准时的次优锚点**：① 目标实现的录屏/截图做目视基准；② 用**不经过被测映射**的
可见语义点反查（如"屏幕上的头/胸/髋三点应分别落入对应判定框"）；③ 逐字段 diff 对照组证零回退。
只做"自己算一遍再和自己比"的回归 = 验证自洽性，不是验证正确性。

- **判"动作真的有效"要同时满足两条**：① 正在播的 motion 的 `_motionData.curveCount > 0`；
  ② 取该 motion 自己的曲线 Id，`getParameterValueById` / `getPartOpacityById` 的值随时间变化。
  只看 `state.currentGroup` 变了没有，会让 `"Curves": []` 的空壳全部绿灯通过
  （本项目就曾因此报出"260/260 全通过"，而实际 57% 是空壳、其余曲线名全错）。
  按部位点击的断言同理：别只断言组名标签，要断言内容。
- **采样必须在 clip 时长内高频密采，不能在载入若干秒后才比对两点**：本项目运行时把**每条 idle 都解析成 `isLoop:false`**（与 motion3 的 `Meta.Loop:true` 无关），idle 播完一遍即回静帧、`state.currentGroup` 归 null、参数回落到基准。若"载入→等 9~12s→两次快照逐参数相减"，短 idle（5~8s）早已播完 ⇒ 假报 `moved=0`（曾据此误判新换入的 `bunao_3`/`guanghui_9` 坏了）。**正确做法**：载入并进入该 clip 后，每 ~420ms 推一帧（手动 `PIXI.Ticker.shared.tick()+app.render()`）、**累积每个参数跨帧 min/max**，判据=「播放窗口内 `max-min>1e-3` 的参数条数 > 0」。另注意手动 `startMotion(group,0,FORCE)` 会与页面自动播相互打断，验证"用户打开即所见"时**别再手动 startMotion**，直接密采。

批量验证 260 个模型时的做法（驱动细节见 `headless-chrome-cdp-batch-export`）：

- 页面内串行遍历：`await renderLive2D(ship, sk)` → 等 1.5~2s → 读 `state.currentGroup` 与 `motionManager.definitions` 数。每轮先 `stopLive2D()` 释放，否则 WebGL 上下文/纹理堆积。
- 断言落在**产品语义**上，不要落在"我猜它不该命中"上。例：断言"有判定区的模型任何点击都不该播出 `touch_*/tap*` 兜底组"，而不是"点某个自算的空白点不该有反应"——后者会因 `toGlobal → 屏幕坐标 → toLocal` 往返误差在极端点被放大而恒失败。
- 冷启动（删过 profile 后）页面里访问 `window.GALLERY` 之类全局数据要先轮询等待，否则 `ReferenceError`。
- **两个 chrome 实例并发跑 CDP 会互相抢**，报 `Execution context was destroyed`；批量验证要串行。
- 清理残留 chrome 必须按 `--user-data-dir` 精确匹配进程命令行再 kill，**绝不能按进程名全杀**（会误杀用户自己的浏览器）。

### 7.1 全库规模（数百模型）必须分批起新 Chrome

上面"每轮 `stopLive2D()` 释放"只能撑一小段：**单个 headless Chrome 顺序加载约 110 个模型后 WebGL 上下文耗尽**，CDP 连接断，报 `Connection to remote host was lost`（标签崩溃），与 `l2d_sweep` 的"单次 evaluate 卡住/断连"同类。靠单进程 + 手动释放扛不住全库，必须**换成分批新进程**：

- **切批**：用 `--only "k1,k2,..."` 逗号清单把模型切成 **~40 个一批**（本项目 269 → 4 批），**每批一个全新 Chrome**（每次调用只起一次进程），而不是一个长循环从头跑到尾。
- **冷启动首模型易报错**：每批新进程加载的第一个模型常撞 `window.GALLERY 未就绪` / `stopLive2D is not defined`（harness artifact，非模型问题）。对策：给每批 `--only` 清单**头部塞一个已知良好的预热模型**（如 `lingbo`，不计入统计），或对报错的首项单独复跑；一旦 warm 起来同模型即 3/3。
- **汇总口径 = 按 key 去重取最优**：合并所有分批日志，同一模型 key 在任一批 `ok` 即算 `ok`，避免某批崩溃漏记被误判成回退。
- 实测：分批后 **269/269 覆盖、806/807 命中**，唯一 miss `z46_3`（Special 框嵌套在 Body 内）是 §4 记录的既有"归一化中心距离"歧义，非本轮回退。

### 7.2 验证前端自己挂的逻辑，必须驱动页面的真实入口

## 9. 动作语音与台词层（2026-09-27 补；此前这条只写在决议里，技能一直停在 §8）

模型动起来之后下一层是"点它会说话、说的有字幕"。八条，每条都对应一次真实返工：

1. **不要用运行时库的 Sound 通道**（`definitions[g][0].Sound`）。那条由 SoundManager 托管，**下一条动作一 `startMotion` 就把上一条 dispose 掉**；而 idle 播完会自动回落 idle ⇒ 凡是"动作时长 < 语音时长"的组都会话说一半被掐（实测 `touch_head` 动作 5.17s、语音 9.24s，在 `currentTime=4.48s` 处被 `pause`）。改成**页面自持一个 Audio 元素**：只有用户再次触发、切标签、换皮肤才打断，运行时回落 idle 不打断。⚠️ 动作时长本身是忠实的（`Meta.Duration` == 曲线末帧 == 源 clip），别去数据层找原因。
2. **首播竞态**：语音表是异步 `fetch` 的，模型就绪那一瞬播的动作拿不到 Sound ⇒ 表现成"第一个动作没声音，之后才有"。开播前 `await` 表到位。**加了台词层之后要把正文表一起等**，否则同样的位置换成"有声没字幕"。
3. **取词按皮肤序号，不许随机抽**：cue 名尾部的 `_N` 是**该语音包内的皮肤档位**，不是"同一条台词的随机变体"。导出侧按本皮肤档位选档，前端一律直取。当成变体随机抽的后果：三皮肤船有 2/3 概率播到**别的皮肤**的台词，且 `_9`（改造皮肤）永远取不到。⚠️ 但**这个档位不等于皮肤行 id 的末位**——皮肤序号 ≥10 之后游戏给新皮肤换了号段（第二位 0→3，末位变成批次内顺序号），把两者当同一个数就是 §86 那次整页台词派错船的起点。另：**画法变体（同一张皮肤的另一幅画，如 `_n`/`_hx` 后缀）不是另一张皮肤**，做"一个目录名分一个档位"这类分配时要把它们排除、直接继承本皮肤，否则变体占掉别人的档。
4. **正文与音频必须同源——"同一档位"，不是"同一行"**：❌ 旧写法 `皮肤行id = cv*10 + idx`（拿语音包号和档位反推主键）在皮肤序号 ≥10 处会**进位撞进下一艘船的那一行**：行存在、正文非空，`if not row` 这类护栏根本不响，只有"字幕比语音短"这种人耳判得住的矛盾会露出来。⇒ 行 id 要**按皮肤名查权威表得到**（查到后回查那一行的归属是不是本皮肤），且台词表里存 `cv`/`idx` 字段的情况极少，别指望反推。
   两层取值规则：音频用的是**本皮肤档**文件的槽位 ⇒ 正文只许取这一档自己的词，取不到就**空着**（宁缺勿错派）；音频落在**基础档**的船级类别（誓约/资料/委托/强化，皮肤行里通常没这些字段）⇒ 回退到本体那一行。同一 painting 有多行时（META/联动另开一档），要**优先取与音频同一个语音包**的那一行。
   类别名之间的对应（cue 类别 / Live2D 动作组 / 触摸槽 / 台词正文字段）全查 `character_voice` 的 `key ↔ resource_key ↔ l2d_action`，**先断言一个运行时名不对多个字段**（有歧义就拒绝，别猜）。
   ⚠️ 还有一类没有来源的：**活动限定变体**（cue 名带 `_ex<code>`，与本体同 `cat`）在台词表里通常**没有**对应字段 ⇒ 前端必须给它独立标签且**不配字幕**，并按 `cat` 取值的地方把它排除掉；否则同一个类别出两行、字幕一模一样（实测 15319 行）。
5. **字幕条必须挂在"会被 `requestFullscreen()` 的那个元素"里面**。各视图通常把自己的全屏按钮做成 `容器.requestFullscreen()`，全屏时**只有那棵子树**被渲染出去；字幕若挂在容器外面（例如挂在上一层 flex 容器上）就是"全屏没台词"。又因为各视图会 `el.innerHTML=...` 整块重写，这个节点要**按需取用/重建**，不能常驻在骨架里。
6. **`<audio controls>` 在列向 flex 容器里会被压成 0 高**：`flex:1` 展开是 `flex-basis:0%`，容器高度由内容决定时没有剩余空间可长 ⇒ 播放器看不见（点都点不到），但行还在。写 `flex:none` + 固定高，判据量 `getBoundingClientRect().height`。
7. **验收（CDP 无头）七条判据**：① 走真实 UI 路径（点语音按钮 / 点画面 / 点部位），不直接调 `startMotion` 或页面内部函数；② 在页面脚本执行前包住 `window.Audio`，断言新实例的 `src` **属于本皮肤档位**且 `currentTime` 在涨——**轮询到真的走秒**，固定等 1.5s 会把正常文件读成 `cur=0` 报假失败；③ 字幕**逐字**等于表里该槽位正文，且"谁在说"那行是中文类别名（内部键 `complete`/`touch_body` 等于把实现细节露给用户）；④ 开关类改动必须拿到**反向证据**：关 A ⇒ 只剩 B、关 B ⇒ 只剩 A，只验"开着时能用"不算；⑤ 挑一条"**有音频但游戏本来没写词**"的槽位做阴性对照（必须出声且**不弹空字幕框**，这同时挡住"字幕残留上一条"）；⑥ 探针不许依赖上一轮状态——无头 Chrome 被 kill 时不保证把 `localStorage` 落盘，下一轮开局开关可能是关的，**每轮先设基线**；⑦ 取不到页面状态要**硬失败**（顶层 `let` 不挂 `window`，用裸名取；返回非 JSON 直接 raise），绝不让"没测到"长得像"测过了"。
8. **"有正文、没有音频"要有独立一档，且绝对不许伪造播放器**（2026-09-27）：一批皮肤的语音主包没随资产下发、台词表里却齐全。
   三处一起改才通：词表要**多跑一趟**（这类皮肤不在语音表里 ⇒ 由语音表派生的键表收不到它们）、索引要有一个
   "只有文本"的计数位（`voiceText`，且**只在无音频条目上写**，别改动 `voiceCount` 的语义）、标签页的放行判据换成
   `有音频 || 有文本`。渲染时这类行**不生成 `<audio>`**——装了就是个点了不响的假控件；验收把这条当反向证据
   （页面 audio 数只允许等于"确实有文件"那一节的条数）。另：文本类内容要有一条**内容形状断言**（页面上不许出现
   `{namecode:NN}` 这类运行时占位符），结构判据全绿也拦不住"把占位符直接端给用户"。
9. **"这一格没声"有两种，别用一条推理打包回答**（2026-10-02）：**我们没接上**（权威表里有这一行、包也在，只是归属
   算错）vs **上游根本没给这个实体下发录音**（有自己的行但包号不在盘上）——修法完全相反，前者改代码、后者改了就是
   造假。分开它要用**两条互相独立的事实**：表里那一行的主键（→ 包号）逐号去源包目录与已解码目录各查一次。
   ⚠️ 两个代理指标都不许当证据：`voice_actor=-1` 在剧情/变体实体上是哨兵值（不等于无 CV）；"整个号段都不在"是
   按前缀归纳，同一个大段里往往有别的号是下发的 ⇒ 只能**逐包号**判。

## 10. 播放策略层：常驻环境层叠加（2026-10-07 补，2026-10-08 改判；轮播池已撤销）

"某部件在游戏里动、在这里不动"多数**不是数据问题，是播什么的问题**。

- **环境层叠加**：源包 AnimatorController 里 `effect` 常是**独立一层的默认状态**（权重 1.0、
  Override、Loop），与 pose 层并行常驻。Web 端只播一条 clip 就会把它整个丢掉。做法是在
  `internalModel.on('afterMotionUpdate')` 里按墙钟 `%duration` 自己求值写参数——
  **不要进队列管理器**（进了队列，播一次别的动作就把环境层挤到末位，回落后又被盖住）。
  ⚠️ **覆盖范围：默认只写"effect 非常值 && 任何 pose clip 都不动"的参数**（`poseDriven` 之外）。
  两级收窄各有事故：常量曲线会把 pose 正在动的参数钉死（实测 15/224 模型受影响、mingji_2 达 70 个）；
  而"照源包语义整层盖住 pose"虽然运动量更接近游戏（47.7‰ vs 让位 35.6‰，游戏角色区 125.8‰），
  实测症状是**"组件蠢蠢欲动 / 突然消失一下"**——所以盖住只作为反向 A/B 开关
  （`window.__ambMask=true`）保留，别当默认。
- ~~**轮播池**~~ **已撤销（2026-10-07 用户双录像对照否证前提）**：游戏里"不点就不换动作"，
  只维持默认态；把 `idle_list` 当轮播池会造成"每 8 秒一个动作尖峰"的观感，与游戏不符。
  留在这里只作为"如果哪天要复刻调度器"的起点，**不要顺手接回来**。
  池成员若真要抽，按控制器自己的分组（子状态机名 + 顶层 `idle`/`home`/`main_*`），不要按名字正则猜；
  轮播用 `mm.on('motionFinish')` 挑下一条**真实组名**。

**四个必踩的坑（每个都烧一轮取证）**：
1. **别造合成动作组**：只往 `motionManager.definitions` 里塞一个假组，`loadMotion` 会**永不
   settle**（URL 解析要过 settings），结果是 `reservedGroup` 挂着、`currentGroup` 恒 undefined，
   一条都不播。
2. **装池之前先 `groups.idle=null`**：否则库的自动回落会抢先把带 Loop 的单条 idle 起播，
   那条永不收尾 ⇒ 之后所有请求被 `reservePriority >= priority` 判成重复预约。装不上再恢复。
3. **`motionFinish` 要延一拍再发请求**：它是在 `state.complete()` **之前** emit 的，当场发 IDLE
   会被 `state.start()` 以 "another motion is playing" 拒掉。`setTimeout(...,0)` 即可。
4. **关掉 Loop**：轮播期间基础动作若带 Loop 就永不 `motionFinish`。注意预加载好的 motion
   对象要回头 `setIsLoop(false)`，只在 createMotion 里判条件来不及。

**量程这一层不在 motion 文件里**：Cubism 会把参数钳进 moc3 声明的 [min,max]，所以
"曲线 0→2000"可能对应"部件纹丝不动"（实测某参数量程 [0,10]，起播 0.45 秒即饱和）。
判"动没动"必须读 `getParameterValueByIndex` 并配 `getParameterMinimumValue/MaximumValue`
（index 版与 `…ById` 版都在，`ById` 内部就是 `getParameterIndex` + 转调 `ByIndex`），
而且**采样窗要盖过整条 clip**——有的部件要到第 8 秒才动，采 3 秒会得到假阴性结论。

## 11. 运行时语义差异：moc3 的 `repeat` 回绕标志（2026-10-08 实测，见 §123）

**症状形状**：某个部件在**游戏里连续动、在我们这里动到一半冻住**；参数轨迹恰好饱和在
moc3 的 max 上，而 motion 曲线明显写着要跑到量程外。这不是丢曲线、也不是选错 clip——
是**两边运行时对同一个标志的解释不同**。

- moc3 每个参数除 `[min,max,default]` 外还有一个 **`repeat` 标志**；官方语义 = 值超出量程时
  **按量程取模回绕**（Unity 原生 framework 走 `CubismMath::ModF`）。所以"单调爬升远超 max"
  可以是美术刻意的循环相位（本项目实例：下落循环值量程 [0,3]、idle 曲线 0→5.867 的一条直线，
  斜率在 idle/home/effect 三条 clip 上恒等 ⇒ 相位型参数无疑）。
- **vendored `pixi-live2d-display` 0.4.0 完全不认这个标志**：整包字符串 `repeat` 命中 0 次，
  `setParameterValueByIndex` 只有两行 min/max 硬钳 ⇒ 所有 repeat 参数的循环在后半段被抹平。
  判据别靠猜：**拿"越界曲线"与"repeat 标志"做交叉表**——本项目越界 580 条 **100% 落在
  repeat=1 上、repeat=0 越界 0 条**，一次同时否证"美术写错"与"导出写坏"。

**修法（一处原型包装，不要改数据）**：包 `CubismModel.prototype.setParameterValueByIndex`，
对**相位参数**在严格越界时 `val = mn + ((val-mn)%sp+sp)%sp`。

⚠️ **判据不能用 moc3 的 `repeat` 标志**（这是本条最初踩的坑）：实测同一个 moc3 里，标志为 1 的参数
**混着两类**——真循环相位（斜坡型：`0→2000`、`0→5.867`、GL 光扫每条 Δ 都等于 0.81）与普通振荡角度
（`ParamForearmRAngle` 量程 [-30,30]，某条 clip 曲线 -59…9 带 8 次复位）。按标志一律回绕，振荡角度会
从 -59° 瞬间跳到 +1° ⇒ 用户症状「选某个动作时手会消失」。**可用的判据是曲线形状**：
`整条 clip 键值单调 && 至少一个键越界` 才当相位；振荡/锯齿型的越界照旧硬钳（游戏里也是钳住的）。
落地：在 `createMotion`（本来就要解析一遍 Curves）里顺手把相位参数的下标登记到
`coreModel.__phaseSet`，setter 只对白名单回绕。

三条硬约束：

1. **`val == max` 不折**。官方 ModF 会把"刚好等于 max"折成 min，但曲线里常有**刻意钉在 max**
   的键点（实测 75 个：某参数整段 =1.0、某花瓣值 =10.0），折过去就是让部件瞬间消失。
   这条不是洁癖——是**量程内恒等自检**（全部 repeat 参数 × 5 档写入读回，要求 0 失配）抓出来的。
2. **包装体里必须用 `this._model.parameters` / `this.__phaseSet`**，不能用闭包捕获某个实例：
   量程表与白名单都逐模型不同，捕错实例就会拿别人的量程折这条值。
3. **写值的唯一入口是 framework**：Cubism Core for Web 的 Model **没有 `setParameterValue`**
   （只有 `getParameterValues` 等只读绑定 + `parameters.values` 这个 wasm 视图），
   所以钳位/回绕只能在 setter 这一层修；`parameters.repeats` 能读到标志，但**别拿它当判据**（见上）。
   另：`_parameterIds` / `parameters.ids` 实测是**纯字符串数组**，按 `.string` 取会全部落空。

**还有一类"某部件在任何动作里都不动"**：不是钳位，是**那条 clip 根本没播**。查法=对每个候选参数
统计"被几条 clip 驱动、驱动时是常量还是斜坡"（`l2d_curve_shape.py`）；本项目实例：某批前景花瓣
由 `Paramfh` 驱动，而它只在 `effect` 这条里有曲线（0→2000），idle/home/main 全是常量 0 ⇒
只有把 `effect` 当常驻层叠上才会掉花瓣，而那属于播放策略决策，不是 bug 修复。

**验收四条，缺一条不许说修好**：① 直写超量程值读回 = 期望回绕值；② 在**真实播放路径**上
统计"动作层交给 setter 的原始值"确实越界过（直写绕过了动作求值，不能当这条证据）；
③ 接缝处一条"传入→存值"实例（3.0483 → 0.0216）；④ 量程内恒等自检 0 失配。

**仪器陷阱（每条单独就能造出"补丁没用"的假结论）**：
- 无头里 `Ticker` 对 `dt` 有上限 ⇒ 运动相位推进远慢于墙钟（实测约 3 帧/秒），
  11.25s 的接缝要 ~49s 墙钟才走到；**按墙钟给的 25 秒采样窗会整段落在接缝之前**。
  用 `Ticker.shared.tick(合成时刻)` 推时间**推不动**，只能拉长墙钟窗口。
- 两次独立抓帧**不能**逐像素对照（起播相位与物理积分步数不同，t=0 就差几万像素）；
  定位改动面用参数级判据，或在同一次会话里扫值截图。
- 探针不许写死别人的服务器；自带 `http.server` 并在启动 Chrome 前轮询 200，
  失败时打印 `location.href` + `document.body.innerText`——「GALLERY is not defined」
  十有八九是连不上服务器，不是页面被改坏。
- 在原型上叠第二层监视器前必须先存**原始**实现引用（`CP.__origSet || CP[method]`），
  否则第二次运行会把监视器自己当基类，`return base.call(...)` 立刻自递归。
- **做 A/B 对照时，开关本身要回读确认生效**：本轮测 `CubismConfig.setOpacityFromMotion=true`
  那一臂"台阶没变"，但打印里没能带上这个标志的实际值 ⇒ 那次"没用"不算结论。
  通用形状：任何"关掉/打开某行为"的对照，都要在同一份输出里回读出**它此刻的真值**，
  否则"配置没生效"与"这条路无效"长得一模一样。

**显隐类症状（"某个部件闪一下 / 消失一下"）的三条判据（2026-10-08 实测）**：
- **先分层，再猜原因**：逐帧同时采 `getPartOpacityByIndex`（全部 part）与全部 drawable 的
  `getDrawableOpacity`，看台阶落在哪一层。实测形状 = **195 个 part 全程恒定、770 个 drawable
  有 188 个在变** ⇒ 隐藏是**逐个 ArtMesh 自己的透明度**做的，与部件组无关——顺带否证了
  "PartGroup 在 motion 起播时 `reset()` 按 `i==e?1:0` 写 0/1，与交叉淡化权重叠出中间档"这条假设。
  不做这一步就会在错误的层上找正确的 bug。
- **事件"次数"不能当判据**：采样窗按墙钟切、动作时间推进又不均匀（上面第一条仪器陷阱），
  同一条 clip 两次跑出 10 与 20 次。可比的只有「同一批成员是否反复出现」与「两臂之差」。
- **计数为 0 必须先证"采到了"**：一条臂管道没接通时同样打印 `0`，而「没跳变」与「没采到」
  长得一模一样（本轮真实踩到：`--allparams` 报 `groupParams:0`，被读成了"参数层没问题"）。
  任何计数判据都要在同一份输出里带上**实际样本数**；管道没接通就先摘掉那条臂并留 TODO。

## 12. 把"某个部件闪一下"归因到运行时：四臂取证法（2026-10-09 补；修正 §11 末尾三条判据里的两条）

前面 §11 那三条判据（先分层 / 次数不算判据 / 计数 0 要证采到了）方向是对的，但落地时**每一条都不够**：
分层只告诉你"落在哪一层"，从"drawable 在变"到"是哪个参数、谁写的、该不该变"还差三步。本轮把工具做成四臂一条命令：

**臂① 分层**（原有）：逐帧同时采全部 part 与全部 drawable 不透明度，两档筛台阶（hard：`<0.05` 且前帧 `>0.5`；
soft：单步降 ≥0.4 且 4 帧内回升 80%）。

**臂② 全参数逐帧 + 台阶形状**：从 wasm 实时缓冲 `parameters.values` 整段取（别逐 index 走 framework getter，
慢且容易错位），对每个参数找**孤立跳变**：`|Δ| ≥ 4× 该参数窗口内 |Δ| 中位数`，且前后一帧 ≤0.35 倍。
⚠️ **绝对不要用"与台阶同帧变化"当判据**——物理/呼吸/常驻层参数一直在动，实测命中 246/532，等于没有判据；
换成孤立跳变后同一窗口只剩 7~10 个。

**臂③ 写入者归因**：包 `setParameterValueByIndex`，只记"存值真的变了"的行（否则会淹没在每帧重复写入里），
附 `Error().stack` 前 4 帧压缩成 `函数@文件:行`——一次读就能分清"复位定时器 / 常驻层 / 动作求值 / 物理"。
⚠️ **`weight` 参数不能用来判"是不是交叉淡化"**：调用方可能把**已经混合过的结果**当值传进来而 weight 恒为 1。
真正的证据是**同一下标每帧被写几笔 + 存值序列**（实测：交叉淡化时每帧两笔，淡出条目交出的值并不等于它自己
clip 的曲线值 ⇒ 中间态既不属于上一条也不属于下一条，这就是"闪一下"的可修部分）。

**臂④ 反查"谁能改这张 ArtMesh 的透明度"：用运行时因果扫描，不要解析 moc3**：
`stopAllMotions()` + 关掉常驻层 → 逐个参数在量程内写 **N≥10 个点** → `core.update()` → 读目标 drawable 透明度，
直接得到**值→透明度映射**（隐藏阈 / 显形带在哪）。532 参数 × 11 点 ≈ 5,852 次 update、约 30 秒，可接受。
⚠️ **扫描点数必须 >2**：ArtMesh 透明度是**乘性带门**（band）——实测同一个 mesh 在 v=0 时 1.00、v=0.3 时 1.00、
v=0.4 时 0.00，只测 min/中/max 三点会**把这个驱动者整个漏掉**（3 点那轮只答出 1 个参数，10 点扫出 10 个）。
推论：**任何"逐参数探测"的扫描，点数必须覆盖整个定义域**，单调假设不成立。

**采样基准必须是「每一次模型 update」而不是墙钟**：包 `CubismCoreModel.prototype.update`
（打补丁前先 `CP.__baseUpdate = CP.update` 存原始实现，否则第二次运行把监视器自己当基类，`base.call` 立刻自递归）。
无头里 update 只有 ~2.6 次/秒，按墙钟数台阶次数同一条 clip 会跑出 10 与 20 两种结果；按帧对齐后绝对次数才第一次可比。

**每条臂都要自证"采到了"**，且要带一条**结构性矛盾**当哨兵：core 的输入只有「参数值 + part 透明度」，
所以"有 drawable 在变而 0 个参数在变"是不可能的 ⇒ 一旦同时出现就是仪器坏，不是"参数层没问题"。

**判据（点名一个参数要四件同时成立，缺一不许说"锁定了"）**：drawable 台阶所在帧 = 该参数的孤立跳变帧；
扫描映射里该参数确实能产生这个透明度值；setter 日志里那一刻有人写它；**权威数据侧的曲线值能解释台阶的终值**。
最后一件最容易漏，也最容易翻案：本轮前三臂都指到"运行时造的值"，是第四件（motion3.json 里 `home` 的曲线
起点=0.5、`idle` 恒 0）证明**那 5 片本来就该消失**，问题只剩中间那一档。

**两条比测量更硬的结构性排除**（先查它们，能省掉一整轮）：
① `model3.json` 有没有 `FileReferences.Pose` —— 没有就根本没有部件组模块，"PartGroup 起播 reset() 写 0/1"
这类假设直接判死，不必去测 part 透明度。② 运行时包里有没有 `setDrawableOpacity` —— 没有就锁死
"drawable 透明度只由 core 的 update 写"，反查目标只剩参数与 part 两个输入。

⚠️ **修正 §11 的一条对照设计**：「不切动作的对照组 = 0 次 ⇒ 症状绑切换事件」**不成立**。带门开合往往是
**周期性**的（由常驻层驱动），对照组窗口落在相位外就是 0 次、落进来就是 1 次——实测同一条对照跑出过 0 与 1。
要判"绑事件"，对照组必须覆盖 ≥1 个完整周期，否则它没有否证力。

**拿到全量绑定表之后，真正该做的是"差集 × 可视性"交叉，而不是继续逐帧采样**（2026-10-09 实测）：
把「A 状态动画、B 状态不动画」的参数差集，与「哪些参数管 mesh 显隐」的表求交，再筛掉
"有第三层（常驻/覆盖层）会把它写回同一个值"的那些 —— 剩下的就是**持续状态差**（进了某状态就一直不对，
切回来才好）。这类问题逐帧采样看不见：它不是瞬态台阶，而是两条运行时语义（"未动画的参数写默认值"
vs "参数持久保留"）的分叉，症状会被误读成"闪一下"。口径提醒：这种表的计数是**下界**——
乘性带门下，基准里已关掉的对象对任何输入都不响应，换基准复扫会多出驱动者。
另：正面证实需要权威侧观测（录像/参照实现），只有"引擎开关确实打开"这种间接证据时，
要在文档里标**前提未证**，不要先改产品代码。

**做 A/B 差图前必须冻住渲染循环**（2026-10-09 实测）：两次截图之间若 ticker 还在跑，物理/头发会继续推进，
姿态漂几像素就让**全身轮廓**在差图里亮起来——同一对图，不冻 ticker 差 3.49% 像素、冻住后只剩 0.08%
（差 43 倍），而那 3.49% 会被读成"这个参数管一大片"。做法：`app.ticker.stop()` + 每次截图前把**全部**
参数恢复到同一基准。推论：差图只用于**身份识别**（把 `ArtMeshNN` 编号对应回画面上是哪一块），
不能当"改好了"的验收证据。

**拿抓帧序列跟参照（游戏录像/基准视频）对比，第一步是钉住动作时间**：无头里手动推 ticker 时动作时间与
墙钟不成 1:1，实测同一"秒数"两边差了约 10 秒的 clip 进度 ⇒ 看起来是"内容不一致"，其实只是"相位不一致"。
每帧必须同时记 motion 队列的时间戳，按 clip 秒对齐后再比；**没对齐的帧对比一律不作数**。

**"谁影响谁"的扰动扫描：基线取在对象的关闭态 = 人人都有影响（假阳性，2026-10-09 实测灌了 95% 的水）**
本项目第一版全量绑定表报"504 个参数管显隐、22,028 组关联"，加了两条之后降到 **99 个 / 1,061 对**：
① **基线必须是确定性姿态**（全部输入写格式声明的默认值后再采基线；拿"运行中恰好停住的状态"当基线，
   凡是此刻为 0 的对象，对**任何**输入的扰动都会报"变了"——那不是因果，是"离开 0"）；
② **一条关联只有在"各采样点读数不是全等"时才算真绑定**（11 点全等于同一个非基线值 ⇒ 与输入无关，丢弃）。
通用形状：任何影响面扫描，先问"基线是不是被测对象的关闭态"；并给出被剔除条数当自证（`nFlatRejected`），
剔掉 0 条和剔掉 2 万条是两件完全不同的事。

**截图类 A/B 有**三道**会各自独立造成"两张图一模一样"，缺一就误判"这个开关没作用"**：
① 写产物缓冲必须打在引擎重算**之后**（在 `core.update()` 之前写 `drawables.opacities` 会被按参数重算覆盖，
   实测写 0 读回 1）；② WebGL 画布默认 `preserveDrawingBuffer=false`，不经过一次合成
   （`render()` → `await requestAnimationFrame` → 再 `render()`），`Page.captureScreenshot` 取到的是**上一帧**；
③ 页面自己的调度循环会把参数写回去（要关 `autoUpdate` 并停调度）。
⇒ **成对截图必须自带像素差自检**：两图差 <50 像素就打印"仪器坏"。"没截到"与"没作用"长得一模一样，
本项目因此把一组 mesh 的身份误判过一次（把"可能是手"说成"是花瓣"），判据来自坏图。

**手工改一个"每帧被控制器重申"的输入，必须先停掉那个控制器**（2026-10-09 实测）：给 Live2D 参数面板拖滑杆
毫无变化，不是"没热更新"——滑杆写 `setParameterValueByIndex` 之后，在播的 clip 下一帧就按曲线把同一个参数写回
（实测一条 `idle` 就驱动 531/532 个参数）。**推论：任何"运行时每帧重申状态"的系统（动画、物理、AI 决策、
状态机驱动的配置），想手验单个输入，要么先暂停驱动方，要么把断言改成"看下一帧之后还剩什么"。**
同一形状也解释了为什么"藏 mesh / 改参数"这类取证必须在**对象本来可见的姿态**下做：
在 setup 默认姿态里被遮挡或在画外的部件，藏与不藏逐像素相同，会被误读成"这块部件不存在/这个开关无效"
（本项目 `--hideclip home` 那一测自检报 0 像素差，就是这个成因）。

**A/B 截图必须打在"同一次定格"上，否则像素差量的是相位漂移不是被改的东西**（2026-10-09 实测）：
做"藏掉这组再拍一张"的身份识别时，如果两次截图各自 `startMotion + 等待`，那是**两次独立播放**——
物理、发丝、动作相位都不重合，差值里绝大部分是漂移。实测出现过"该组 29 片当时全是暗的、藏了理应零变化，
却报 1 万像素差"，也出现过"确实藏掉了 5 片、只报 1569 像素"——**两个方向都会错**，所以这类像素数
只能当"截图有没有在动"的弱自检，不能当结论；结论要靠**肉眼看同一帧的两张图**，或改成
同一次定格上先拍 A、再改状态拍 B（中间绝不重播）。
配套自证三件套（缺一样就会把仪器故障读成产品事实）：`实际在播哪条 clip`、`被改对象此刻亮着几片`、
`其中几片在画面内`——本项目就是靠这三条才发现"零像素差"的原因是**角色整个在画外**。

**"先定格、再扰动"的基线必须自己跟自己一致，否则它混进了第二套没被固定住的状态**（2026-10-09 实测）：
把运行时停在某一帧、再逐个输入扫量程——看似严谨，但**同一组输入在"读基线"时和"扫描中"给出不同输出**
（本项目：定格读到目标全灭，而扫描里同一个参数值却把它点亮）。说明被测系统除"当前输入"外还有
**只由历史写入、不随输入重算的量**（Live2D 里就是 part 透明度：由动作写入，停动作后停在半途）。
⇒ 规则：这类基线扫描**必须自带一条恒等自检**——扫完回到基线输入重读一次，要求与最初基线逐位相同；
不等就先找那个"第二套状态"，别用结果下任何结论。另一条同时成立的教训：**找"开关的门"时，
单参数扫量程在乘性多门下会漏**，要配一道反向探测（其余保持基线值、只把这个改回默认，看目标是否亮起）
才找得到"正在挡路的那个输入"。

**"挡路者"式反查的判据必须是"相对基线变亮"，不是"读数 > 阈值"**（2026-10-09 踩到）：
反查"当前是哪个输入把目标关着"时，若同时观测多个目标，判据写成 `读数.some(x>0.05)` 会被
**本来就亮着的对照目标**满足 ⇒ 报出一大串"挡路者"，而它们的读数与基线逐位相同（本项目一次报了 191 个，
全是假的）。正确写法：`读数[k] - 基线[k] > 阈值` 且只对"基线里灭着"的那些位判。

**同一模型可能有两套 id 数组，跨臂引用前必须逐位自证**：本项目臂 ⑤ 用探针自装的 `__drawableIds`、
臂 ⑩⑪ 用引擎的 `drawables.ids`，两者一旦错位，"某片在实态里是灭的"这种结论就完全失去意义。
⇒ 读别的臂产出的名字时，回显 `[名, 两套数组各自的下标, 两个长度, 是否逐位相同]`，
让"错位"在**同一行输出里**暴露，而不是靠事后对不上再猜。

**「整组为空就回退」这类兜底，上线前先量它在正常帧里有多少次为真**（2026-10-09 试错后撤销）：
想消掉切换/穿带时的闪烁，最自然的规则是「某个输入所管的那组对象整组都不渲染时，把该输入退回上一次
「组里有东西」的值」。在 Live2D 上实测撤销，原因是**聚合粒度错了**：33 个开关参数各自的「美术家族」里，
有 18 个家族在**任意一帧**都是全灭的——它们本就不属于当前动作（换装变体、另一套手、场景件）。
于是「整族全灭」这个信号**不区分「该灭」与「闪了一下」**，兜下去一帧都没救回来，
反而在家族正常关闭时把参数多钉 0.4 秒（让本该消失的美术留在画上）。真正的闪烁发生在**家族内的子组**：
子组全灭、同族其它成员还亮着。⇒ 通用规则：任何「聚合为空即异常」的判据，先测它在正常样本里的发生率；
**若在大多数正常帧里都成立，它就不是缺陷信号**（本项目是 100% 的帧都有 18/33 个家族全灭）。

## 13. 修掉"切动作瞬间整组美术消失"：交叉淡化里钉住互斥美术开关（2026-10-09 实测落地）

**失效形状（长得像数据坏，其实是切换语义差）**：源数据里有一类参数被美术当**两套互斥美术的开关**用
（v=0 用 A 组、v≥0.2 用 B 组、**中间一段两组全灭**）。游戏侧是运行时瞬时切换（Unity 的
`Animator.Play()`，状态机里**一条出边过渡都没写**）⇒ 值一帧跳过去，永远不落在中间那段；
网页侧为了"姿态不硬跳"保留了库的交叉淡化 ⇒ 值被平滑插值 ⇒ **必穿全灭区间**
⇒ 观感 = 每次切动作有零点几秒"手/翅膀/某整组部件没了"。
⇒ 排查顺序：**先读源包状态机有没有过渡**（有过渡才谈淡化时长），再决定改哪一侧。

**修法形状**：不要整体取消淡化（那会把"姿态硬跳/塌帧"放回来），只把**开关类**参数在切换窗口内
逐帧钉在「进来的那条 clip 的边界值」上，其余参数照常混合。判定表离线生成、随模型放一份 sidecar；
**表不存在 = 这一层完全不存在**（绝不留"空表也跑过"的假成功）。

**"哪些算开关"必须因果判定，三条同时成立**（名字后缀、曲线形状、量程标志都会误伤）：
1. 它真的能改变某个 ArtMesh 的不透明度（运行时逐个输入扫量程得到显隐台账；本项目 532 个参数里只有 99 个有这能力）
   —— 这一条自动挡掉相位/口型/角度类，因为它们根本不碰显隐；
2. 切换前后的两个边界值之间**跨过台账里的翻转点**；
3. 它在量程内的**几何位移够小**：把其它输入全钉在基准，只移动这一个，比较**两点都亮着**的 mesh 的
   屏幕框 Σ(宽+高) —— 纯显隐开关应当一像素都不动。
   这一条专治"既绑显隐又是姿态"的参数（本项目 `ParamForearmLAngle`：位移 27.8 屏幕单位 / 阈值 0.5）。
   位移分布通常是**双峰**的（一批恰好 0，一批 1.5 以上），阈值取在空档里，别取"看起来小就行"。

**四条硬事实（每条都会让判据悄悄失效）**：
- **不透明度为 0 的 ArtMesh，顶点缓冲会塌到原点** ⇒ 从任何单一姿态导出都拿不到"灭着那组"的尺寸，
  **面积/覆盖类判据是死的**；要量几何只能在真的点亮它的那一拍读。
- **"亮着的 mesh 个数"也不分辨**：开关从 0→0.1 时 A 组 5 片灭、另一组正好 5 片亮 ⇒ 个数不变。
- **只能钉住"所有写入者都排在你前面"的输入**。Live2D Cubism4 内部模型的次序是
  motions → (你的 `afterMotionUpdate` 钩子) → saveParameters → expression → **eyeBlink** → focus →
  naturalMovements → physics → `core.update()` ⇒ 眨眼/口型/物理驱动的参数用这层钉不住（会被后面的层盖掉），
  它们进了名单也是白进 —— 所以名单要配一条"是否真被钉住"的实测，而不是只看名单长度。
- **钉多久**的上限是"该值在源 clip 里真正恒定的秒数"，算法是**连续等值键段的跨度**，不是"第二个键在哪"
  （四个键都等于 0.5 时后者会把 2.9s 算成 1.55s，后段又漏回死区）；而实际淡化时长要取
  **两条动作各自 fade 的较大者**并按实测校准，不要照搬配置里的单个 `FadeInTime`。

**验收判据（动态问题不要拿静态图当证据）**：同一趟跑两个模式（修法开 / 关，靠一个
`window.__xxxOff` 反向开关），**逐次模型 update** 记一行时间轴，看"该输入能影响的全部 mesh 里有几盏亮"
随帧的曲线：修法关时它必须掉到 0、修法开时全程 >0。截图只用于认画面身份。
两个模式必须各自自证"表真的加载了"（读一个 `window.__xxxDbg()` 报 `state:"ok"`），
否则整轮 A/B 测的是"补丁没生效"。

**⚠️ 无头浏览器会伪装成"补丁没生效"**：固定 `--user-data-dir` 的 headless Chrome 改过前端后端出的是
**磁盘缓存里的旧 HTML**，症状是"代码明明落盘、跑出来的行为与改动前逐帧相同"，而且调试函数报
`NO-SUCH-FN` 看着像"代码没执行"。⇒ 探针 URL 一律带 `?v=<epoch>` cache-buster；
判"前端补丁无效"之前先证页面是新的。

## 14. 把「参数 → 显隐」扫成表之前，先证这张表是函数表（2026-10-10 实测；编号从 §12 改来，原文里另有一条 §12 是"四臂取证法"）

**症状形状**：逐档爬的因果扫描（把参数按 0→0.1→0.2… 写一遍、每档读全部 mesh）产出的表，
拿去复现时对不上——**同一份参数数组，冷态读 0、被扫过之后读 1，而且写回基线不还原**。
这不是"谁写错了"，是**滞回**：这类扫描的"阈值"其实是**扫描网格的中点**，连"哪几片属于同一族"
都是同一假象。基于这种表做的"钉边界值"修法只能修掉一部分，剩下的会以"中途闪一下 / 半透明"回来。

**唯一可信的扫描形状**：① 每个测量点都**从基线一次跳到**（中间不许路过别的档）；
② **正序 + 倒序各跑一遍**，两遍逐档一致才允许发布；不一致就只能说"有滞回"，**不许说阈值**。
"跳过去再跳回来"还要各读若干拍，用来区分"第几拍才结算"与"真不随参数变"。

**三把必须自带的仪器自证**（缺一把就会把仪器故障读成"这条路无效"）：
1. **三种读法对照**：手里缓存的 `core._model.drawables.*` 旧视图 / 每拍重新取的视图 / 框架 getter
   （`getDrawableOpacity` 等）。不一致 ⇒ wasm 内存增长后 typed-array 视图失效，整张表作废。
2. **两条写路径对照**：直写 `parameters.values` vs 走 `setParameterValueByIndex`。
   不同 ⇒ 之前的测量绕过了真实播放路径，结论不能用于播放。
3. **逐位 diff 参数数组**：写完基线、update 一拍，再把缓冲与"我们写进去的值"逐位比。
   非 0 ⇒ moc3 里有**派生参数链**，扫出来的"阈值"量的是派生值的运动，不是这个参数。

**另外两条本轮真实踩到的坑**：
- **像素对照必须驱动 `model.update()`**：每片的 alpha 是在 `model.update()` 里从 core 缓冲同步的，
  只做 `core.update()+app.render()` 就宣布"缓冲变了而像素没变 ⇒ 这块缓冲不管渲染"是错的读法。
- **别拿不存在的键名做"否证"**：`drawables.partMatch`、`parts.defaultValues` 在 Cubism Core 的 wasm 视图里
  根本没有（真名分别是 `parentPartIndices`，以及**没有默认值数组**）。`undefined` 参与减法得到 `NaN`，
  所有比较都是 false ⇒ 会稳定报出"0 个异常"，长得像"这条嫌疑已否证"。
  ⇒ **任何"计数为 0"的否证，都要先证那个键真的读到了东西**（打印 `Object.keys(视图)` 与一个样本值的类型）。

### 14.1 本节写完当天就被自己证伪了一半：**「一跳 + 两遍一致」仍然不够，一页只有第一次探测可信**（2026-10-10 续测）

上面"唯一可信的扫描形状"（每点从基线一跳 + 正倒序各跑一遍要求两遍一致）实测**过不了**：
同一次会话里逐值扫，`drift`（复位后仍不等于冷基线的片数）与变化片数**只增不减**、
还会**跨参数往下带**（A 参数 0→29 ⇒ B 参数 29→53 ⇒ C 参数恒 53）。⇒ 不是"扫描形状不对"，
而是**这类模型的部分显隐根本不是参数的函数，而是路径函数**（key-value 式"路过才写、写了不灭"）。

**判"到底是滞回、慢收敛、累加器、还是读错缓冲"的四把对照**（缺一把就会把仪器问题读成物理问题）：
1. **探测拍数 A/B**：同一批值，一套"先复位打一拍、再打目标值一拍"，一套"写成目标状态只打一拍"。
   残留序列**逐位相同** ⇒ 不是多打一拍造出来的。
2. **同值连探 4 次**：每次残留都是**同一批片** ⇒ 幂等，排除"累加器越探越亮"。
3. **复位后连打 N 拍（N≥200）**：残留不打掉 ⇒ 排除"慢收敛、显隐滞后几拍才结算"。
4. **不同值各自的残留集合**：值 0.1 与 0.5 钉住的是**不同的片**，而升序访问的残留 = 各处之并
   ⇒ 排除"某条臂读错了"，同时给出锁存项的名单。
外加两件事必须查：**逐一试复位手段**（直写片缓冲 / 写回基线 / 只写参数默认 / 框架 setter / 写 part 默认 / 组合），
**并列出运行时真实存在的 reset 类 API**（本项目 core 上只有 `getParameterDefaultValue` 与 `initialize`，
即**没有一键复位**，只能重载模型）。别猜 API 名字——把 `Object.getOwnPropertyNames(原型)` 打出来。

**要量一条真曲线，代价就是"一页一个数据点"**（每页：冷基线 → 一次跳到该值 = 该值的干净响应 R(v)
→ 回默认打一拍并连打 N 拍 = 该值自己留下的锁存项 L(v)）。所以**值表 = 成本**：先只量一个参数、
几个关键值，别一上来铺全库。页与页之间要核对"各页的冷基线逐位相同"，不同就说明冷基线不可复现、整批作废。

**下游推论（写进判据，别再走回头路）**：一旦确认是锁存，任何"按当前参数值该显示什么"的阈值表
（含"切换时钉边界值"那类修法）都在问一个不存在的问题——钉值还会**跳过中间刻度**，从而少点亮只有
路过该刻度才会亮的片。正确的提法是**"参数轨迹路过哪些键、按什么顺序"**，比对齐要沿这条轴做。

**用画面像素反查"某块美术短暂变淡"时的两条必踩坑**（2026-10-11 实测，两条都把检测器打穿过）：
- 拿**八邻域**当共模去否证 ⇒ 目标物比一块大，真变淡时邻域一起跌，**所有真信号被否掉**（表现为 0 命中，
  极易被读成"对面没有"）。共模要取**整幅 ROI 的中位数**。
- 换成整幅共模后，**大幅运动的主体**会让皮肤/边缘像素不断进出网格 ⇒ 一次跑出自称合理的一大堆命中
  （本项目 287 处，全部可由挥手解释）。⇒ 这类像素检测**不许下阴性结论**，除非先在
  **同一条 clip 的自己渲染帧**上把已知那几帧抓到（阳性对照），检测器才算有效。
  判"游戏里有没有出现过某个画面"，优先用**与相位无关的结构性证据**（如逐次 update 的亮着片数跳变次数），
  而不是像素检测。

**跨来源做"帧序列对齐"（DTW 之类）之前的三道必查项**（2026-10-11 一次全错到位的实测）：
- **最优路径自带"自洽"**：DTW 总能找出一条内部一致的路径。上一版把"面积差/一边有一边没有"算进代价，
  它给出的路径中段斜率 1.00 看着完美，**配对图里却是游戏站姿对上我们倒立**。
  ⇒ **任何对齐结果都要出一张"每行：A 帧 | B 匹配帧"的目视复核表**，没有它不许报对齐结论。
- **零假设对照 = 把 B 序列时间倒放再对齐一次**：正放与倒放的总代价差不多（实测 9665.1 vs 9667.6，差 0.03%）
  ⇒ 描述子根本没有判别力，**本轮所有对齐结论一律不许下**（这条判据要写进脚本，红了就退出）。
- **先量描述子的可分辨性**：跨来源（游戏录屏 vs 自己的渲染）取景尺度差一个数量级时，
  "缩到 24×24 归一化贴片"必然无判别力；而且**颜色掩码可能锁在静态 UI/底纹上而不是角色上**——
  自证方法：看掩码包围盒是否**随时间不动**（实测我们那侧恒定 302×192 而像素数 1429↔168 跳 ⇒ 锁错对象）。
  ⇒ 能做参数空间对账的就别走像素：我们侧的参数可以逐帧精确记录，游戏侧不行。

实测数字与本案细节见 `docs/TROUBLESHOOTING.md` §123 追加-XV；测法脚本
`scripts/diag/l2d_part_flicker_probe.py` 的臂 ⑰/⑱/⑲（`--coldmapall` / `--latchreset` / `--latchlaw`）。


### 14.2 「这组 mesh 就是画面上那块」是**名单假设**，必须用离屏渲染反查一次（2026-10-11 实测：本项目在这里白耗了十一轮）

台账/锁存律这类中间产物给出的分组（"A 组手 / g01…g06"）**只是名字相近的假设**，不是证据。
本案的 34 片"手"名单来自「参数扫出来的显隐家族」，两条独立对照证明它们**根本不是画面上那两只手**：
只留这 34 片渲染时 `home` 第 4 秒画布**零不透明像素**（压根不在取景里），而逐组 hide 任何一组，
画面上的手一次都没变。⇒ 之前每一轮"亮片数没掉到 0"量的都是看不见的美术。

**必做的三条仪器约束**：

1. **显隐判据必须两栏**：`亮 := opacity>0.5`、`看得见 := 亮 且 bbox 面积 > eps`。
   Live2D 藏一套美术有两条通道（透明度 / 绑定缩放归零 ⇒ 顶点坍缩），只读前者对"亮着的空壳"全盲。
   另注意 `vertexCount` 恒 >0 且首顶点坐标是**真值**——"面积为 0"多半是"这片当前没亮"，
   别把它读成"模型里没有这块几何"。
2. **反查名单用离屏渲染，不用推理**：把**除目标片以外**所有 drawable 的透明度打 0（必须打在
   `coreModel.update()` **之后**，否则会被按参数重算覆盖），抓一张**带 alpha** 的 PNG，
   离线 `img.split()[3].getbbox()` ⇒ 得到该片在**屏幕上**的落点与占比。
   这一步同时回答"在不在画面里"和"是哪一块"，是名单类产出的唯一合格验收。
3. **阳性对照要"看图"，不要"算差"**：逐组 hide 各抓一张后，如果去算两两像素差，
   差异会被**位移**吃掉（实测七组的差异包围盒一模一样 = 全画面位移）。
   而且 `renderer.extract` 自己会把模型推进一帧——`app.ticker.stop()` 也压不住。
   ⚠️ 同一个 alpha 通道在不同测法里语义相反：背景美术铺满画布时，比 alpha 会**恒等于 0 差异**（全盲）；
   而"只留目标片"时 alpha 恰恰是唯一正确判据。

**顺带两条会静默作废整批 A/B 的入口问题**：

- **验证脚本必须走页面自己的入口**。直接调 `motionManager.startMotion(...)` 会绕过 `play()` 里的
  副作用（本项目：`played.add(g)` 是"非 idle 动作参数残留复位层"唯一的装填条件，且 UI 路径播完
  会**回落 idle**、直接调则 currentGroup 永远停在该 clip）。⇒ 旧"关/开复位层两边一样"的 A/B
  等于两台都关着做，其否定结论必须作废重测。
- **抓帧时钟**：CDP `Page.captureScreenshot` 一张 0.8~1.2s，模型跟着停摆 ⇒ "第 N 帧"根本不是模型的第 N 帧；
  页面内 `renderer.extract.base64` 是几十毫秒级，且可以**把当时的逐拍读数随图一起存**，
  每张图自带状态签名。时钟原点要钉在 `startMotion` 那一刻，不是页面加载。
- **发布采样率**：逐拍仪器必须把**实测拍率**（update/秒）随结果打印；低于阈值（本案 25/s）就明写
  "这趟测不到几十毫秒级的窗口"，只允许下"≥1/拍率 秒的窗口不存在"这种结论。

本案数字与判死清单见 `docs/TROUBLESHOOTING.md` §123 追加-XX；可抄的测法＝
`scripts/diag/l2d_part_flicker_probe.py` 的臂 ㉒（`--handdark` + `--hdonlyat`（只留目标片量屏幕包围盒）
+ `--hdgrpat`（逐组 hide 看图）+ `--hdui`（走页面入口）+ `--hdshots`（页面内定时截图））。
**要"回到某一帧"时，别复现时钟——复现参数向量**（2026-10-11 实测，省掉一整类假阳性）：

- 姿态由参数决定，不由时钟决定。连拍时**逐张记下当时的完整参数向量**，之后把某个向量写回
  `parameters.values` + 手动一次 `coreModel.update()` + 冻帧 ⇒ **精确回到那一帧**，
  即使 `currentGroup` 早就换成别的 clip 也不影响。比"按秒数重播再找相似帧"可靠得多
  （后者实测残差 RMS 4.28，落回去的是另一个姿态）。
- 因此"这块是谁画的 / 灭着的片里谁在该处"这类反查，必须在**同一个页面会话**里做：
  连拍 → 人挑一张 → 复位 → 反查。跨进程传靶框必然错（截图裁的还是随姿态移动的模型包围盒）。
- **对照项要在动缓冲之前取基线**：强制点亮类测法第一步通常是"把全部可见性写 0"，
  若"当前哪些是亮的"这组对照在写 0 **之后**才采集，就会拿到空集 ⇒ 对照恒 0、整批读数全废
  （本案实测：只有 1 个点有信号，差点据此下"灭着的片里没有第二套手"的结论）。
  擦之前取一次、擦之后再验一次空靶区应为 0，两条都过才算仪器好。

**"要量哪一块"必须由**同一趟页面**回答：先冻住、照这一帧量靶、再就地二分**（2026-10-11 两次假阳性换来的）：

- **不要试图跨进程复现动画相位**。插件的 `motionManager.state` 里没有时间的字段（只有
  `currentGroup/currentIndex/*Priority`），`_currentMotion`/`state.items` 也不存在；
  改用"参数向量当姿态指纹去扫最近帧"同样失败（实测残差 RMS 4.28，复位后角色整个倒立）。
  ⇒ 任何"照着上一次运行量的靶框"都是错的。
- **能用的形状 = 一个页面会话里的两步会话**：驱动轮询一个命令文件 ⇒
  ① `{advance:秒}`：页面放开跑一会儿再**就地冻住**（`autoUpdate=false` + `ticker.stop()` + 手动一次
  `coreModel.update()`），回传当前帧与 `stage.getBounds()`；② `{mode:bisect, box}`：
  我照**这张**帧量靶，同一页面、同一冻帧上逐批藏、比颜色。靶框与画面天然同帧，`advance` 可反复发。
- **反查结果必须"把靶框画回那张图"看一眼再采信**。本案第一次收敛出"某片变色 96%"看着极漂亮，
  画回图上看：框压在月亮上 ⇒ 那一片是背景月亮。数字漂亮 ≠ 认对了对象。
- **闸门要会拒绝**：残差超阈值就 `poseMiss` 中止、不许继续二分——
  宁可没有名单，也不要一份会把人带回死路的假名单（本项目已因此白烧过十一轮）。

**用像素当靶做"这块是谁画的"反查时，还有三条会让整批结论翻车的仪器事实**（2026-10-11 实测，第一次反查因此给出假阳性名单）：

- **`extract(stage)` 裁的是模型自身包围盒，不是画布** ⇒ 同一张图上的 (x,y) 到下一帧就落到别的身体部位上。
  靶框必须换算到**画布**坐标（或每帧同时回传包围盒原点），否则"逐批藏起来看区域掉多少"量的是随机部位。
- **"第几秒"不是相位**：同一个 `--hfat 11`，三趟分别拍到居中举手 / 跪姿举手 / 只露画面底边一对角
  （点击到真正起播之间隔着载入 + 上一条淡出 + 交叉淡化，每次都不同）。
  ⇒ 锚点要用 **clip 自己的时间**（读 motion 的 currentTime），不是墙钟。
- **alpha 覆盖数会被半透明层钉死**：实测整幅 457,835 = 889×515 **每一帧都全不透明**，
  于是"藏掉全部亮片"后靶区读数一动不动，差点被读成"没有一片画在手里"。
  ⇒ 判"这块是谁画的"要**比颜色**（逐像素通道和变化），alpha 只在"只留目标片"那种测法里才有效。
- **冻帧与"藏"互相矛盾，必须手动补一次更新**：`autoUpdate` 开着时每次渲染都推一帧（基线两连测自差实测 53%，
  噪声比信号大）；关掉 `autoUpdate` + `ticker.stop()` 之后自差=0，但"藏"是打在 `core.update()` 之后的，
  没人跑更新就藏不动 ⇒ 每次改完显隐缓冲要手动 `coreModel.update()` 一次（只重算变形、不推时钟）。

## 15. 「暂停冻帧 + 姿态存档」＝把坏帧从用户手里交进仪器（2026-10-11 实测落地）

无头环境的模型更新率只有 **5~14 拍/秒**（swiftshader 下每拍 ~200ms）⇒ **短于 200ms 的症状在结构上测不出来**，
再密的撒网也抓不到。这时候不要继续加采样，要**给用户一个暂停键**：他那边是 60fps，看到不对当场按停就是那一帧。

- **正确的冻结开关是 `Live2DModel.autoUpdate=false`，不是 `app.ticker.stop()`**。
  机制在库的 `_render`：`this.deltaTime && (this.internalModel.update(this.deltaTime, this.elapsedTime), this.deltaTime=0)`，
  而 `deltaTime` 只由挂在 `PIXI.Ticker.shared` 上的 `onTickerUpdate` 累加 ⇒ 关掉它 = motion / 物理 /
  `coreModel.update()` **整条**停住（姿态真冻住），`app.ticker` 照跑（画布仍刷新，缩放平移都还能用）。
  用 `ticker.stop()` 的代价：连渲染一起停，且页面里"在 update 之后生效"的写入（显隐缓冲等）全部失效。
- ⚠️ **凡按 `performance.now()` 取时间的自挂层，恢复时必须整体平移 `t0`**（本项目有三层：参数残留复位、
  环境层常驻叠加、交叉淡化里钉住开关值）。前两层挂在 `afterMotionUpdate` 上，暂停期间根本不触发，无需处理写入；
  但**挂在 `app.ticker` 上的那条会照爬**，攒下的渐变在恢复那一拍一次写完 ⇒ 参数瞬移。
  修法两半：该回调顶部按暂停标志直接 return；恢复时把**所有**层的 `t0` 一起加上"暂停掉的毫秒数"
  （只平移一层就漏——漏掉环境层那一条的症状是滚动/波纹类参数瞬移）。
  另外自维护一个模型时钟 `now() = performance.now() - 累计暂停毫秒`，存档里报"这条动作第几秒"必须用它，
  否则"冻 20 秒再放开"会把秒数报成墙上时间。
- **存档要带什么（只存截图不够）**：图只能说明"哪块没了"；**全量参数向量**才能把同一帧在无头里原样摆回来再做仪器 interrogate。
  本项目一条 idle 存档 30KB：`parameters`（532 条全量向量）/ `parts` /
  `art`（**每片上屏 drawable 的 `[名, 不透明度, 宽, 高, x0, y0]`**，只收 op>0.01）/ `counts{lit,collapsed,…}` /
  `view`（取景，复现同一张构图要用）/ `flags`（页面上那些取证开关当下的值）/ `group` + 第几秒。
  包围盒那一项是关键的第二通道：**顶点坍缩**让美术消失，而 `opacities` 全程是 1——只读不透明度判"在不在"必然漏。
- **单帧的"塌成一个点的有 N 片"不是症状**：正常 pose 里就有一批零面积的**停放件**（实测一条正常 idle 就有 8 片）。
  ⇒ 读档工具必须支持**两帧比差集**（只在对照帧亮着的 / 两边都亮但坏帧里被压成点的），并让单帧模式自己声明"判不了"。
- **验收这类"冻结"功能的三条仪器底线**：
  1. **先证"会动"再证"冻住"**——暂停前逐拍最大相对位移必须 >0；没有这条阳性对照，"参数不变"完全可能只是页面死了。
  2. 恢复跳变要按**"一拍对一拍"**比（差值记在 `afterMotionUpdate` 里、按各参数量程归一），不能按固定毫秒比——
     低帧率下按毫秒比会把一次正常眨眼算成"姿态瞬移"（假阳性）。
  3. 存档落盘要有**服务端命名权**：文件名 = 服务端时间戳 + 清洗过的 tag、body 原样落盘、同秒重复不覆盖
     （连按两次静默吞掉前一条就是丢证据），并把"页面 POST 到哪台服务器"做成可注入 ——
     测试要能自己起一台带该接口的服务器，而不是依赖用户那台正在跑旧代码的（它只会给 501，
     "页面没存档"与"服务器是旧的"必须分得开）。
- **存档目录按"这台服务器正在服务的根"算，不按模块文件路径算**：同一份服务器代码会被两处使用
  （部署目录里的副本、以及探针从源码正本 import 起来起临时服务器），按模块路径算出的"项目根"在后者是错的，
  产物会静默落到项目外面去。
- **回放存档必须自带"走样没"的自证，否则图是假证据**：把参数向量 + 部件透明度 + **每片美术不透明度**写回模型、
  冻住、跑一次 `coreModel.update()`、按存档里的取景截图；判据用「上屏数==存档、参数回读漂移==0、
  逐片包围盒差的**中位** ≤0.02 单位」，不合格在图上打 ⚠ 并非零退出。三条踩过的坑：
  ① **显隐要在 `update()` 之前钉**（core 对不透明度为 0 的片跳过顶点计算，晚钉的那批会停在出厂位置）；
  ② **"只留某几片"的掩码要在 `update()` 之后写**（写在前面会被 core 按参数重算冲掉，出来是空画面）；
  ③ 判据只量"两侧都真画出面积"的片 —— 停放件宽 1~4 单位（不足 1 像素）、回放里还会塌成 0 面积，
  拿它们算最大值会把好帧判死（实测中位 0.004 而最大 28）。
- ⚠️ **抓"当前参数向量"必须在 `beforeModelUpdate` 那一刻抓，不能在帧外抓**。
  库每帧的顺序是 `saveParameters()` → 表情/眨眼/focus/**物理** 改缓冲 → `beforeModelUpdate`
  → `coreModel.update()`（出画面）→ `loadParameters()` **把缓冲还原**。所以帧外读
  `model.parameters.values` 拿到的是**物理之前**的那份 ⇒ 照它回放会凭空少掉一批显隐
  （实测 414/460 亮、46 片"参数解释不了"、停放件包围盒差到 28 单位）。
  改抓快照后：423/423 零缺口、最大差 0.039 单位。存档里带一个来源字段（如 `paramSrc:'preUpdate'`）自证。
  ⇒ 通用形状：**回放对不上先怀疑仪器抓错了什么**，别急着当成产品 bug。
- ⚠️ **"某几片 = 画面上某个部位"这种断言，最后必须在人眼能看的回放图上落一次**。
  本项目同一个坑栽了三次（把月亮当成手、把倒立姿态当成靶、把两片描边/光效当成实心手——
  "只留这两片"的图是空画面才发现）。数字判据再漂亮也不能替代这一步。
- ⚠️ **无头的模型时钟比墙钟慢一个量级**（实测一条 18.25s 的 clip 跑了 32 秒墙钟 `state.currentGroup` 还是它）
  ⇒ 凡判据依赖"clip 播完 / 回落 idle / 某个只活 1 秒的窗口"，**等不到**，必须自己把模型时钟推过去：
  分片调 `Live2DModel.update(120)` 并在片之间 `await` 让出一帧（`update` 只累 `deltaTime`，
  下一次 `_render` 消费掉 ⇒ 走的还是产品自己那条 `internalModel.update`，不是另造假时钟）；
  步长取 120ms 这种"不超过正常步长"的量，别一次推几秒把物理积分推爆。
  而那种 **~1 秒宽的窗口**（本项目：复位层 REST_DELAY 400ms + REST_MS 700ms）**必须在推的循环里就地探测**，
  推完再回头轮询就错过了。
- **用户交来的存档"没有图"时，先查两半通道再重要**：图要**页面 JS 与服务器代码同时新**才会落盘。
  两条零成本反向证据：存档里有没有那个"只在新版才写"的字段（本项目是 `paramSrc`）、
  以及服务器进程的启动时间（`Get-CimInstance Win32_Process` 看 `CreationDate`）。
  任一旧了就只会退回"只有数字"，此时**别把数字当现场**。
- **要"直播真画面"但等不到用户刷新**：走产品自己的入口起动作，关掉 `autoUpdate`，
  然后**自己按固定步长喂 `Live2DModel.update(dt)`** —— 它只累 `deltaTime`、下一次 `_render` 消费掉，
  所以 motion/物理/显隐走的仍是产品那条链，而"clip 第几秒"变成**精确可累计**的整数倍步长，
  能停在用户报的那个时刻上（比"每秒轮询墙钟"准，因为无头模型时钟比墙钟慢一个量级）。
  停住后必须拿**该时刻本该被驱动的那几条参数值**与用户存档比，偏差大的那张图直接判"不能当现场"。
- **依赖某个模型特性的判据要按特性挑模型跑，缺特性打成显式 SKIP**（本项目：残留复位层只处理
  「刚播过的 clip 驱动、而 idle 不驱动」的参数；这块皮肤所有 clip 的参数都在 idle 的驱动集里 ⇒ 那层根本不装填，
  判据永远测不到，而这**不是**产品缺陷）。做法：末行汇总写 `判据全过；SKIP N 条：<原因>`，
  SKIP 既不算 PASS 也不算 FAIL，并另挑一个确实有该特性的模型把同一条判据跑绿。
- ⚠️⚠️ **回放图不是"产品画了什么"的证据；只有画布本身是**（2026-10-12 靠这条撤回了上一轮整份指认）。
  冷启动手动 `coreModel.update()` 里，**core 从不覆写"当时不可见"那些片的顶点缓冲**：实测某模型
  "另一姿势的手"那 59 片在回放里 `op=1` 而 `vertexPositions[i]` 34 个浮点**全 0**（画面上等于不存在），
  直播同一时刻却有 0.5~1.8 单位的实形 ⇒ 回放图上"手没了"，直播图上"手好好在"。
  **再 update 一次也补不回来**（别指望"上一拍可见性决定这一拍"这种想当然）。
  ⇒ 三条硬要求：
  ① **交接通道必须同时带画布图**：`app.render()` 之后立刻 `app.view.toDataURL('image/png')`
    （`render()` 不能省——WebGL 默认不保留绘制缓冲，不先同步渲一次拿到的是空图；
    **空图比没图更坏**，所以验收判据要写"魔数对 **且** 采样颜色种数 >2"，只判"文件存在"等于没判）；
  ② **要真画面就走产品自己的入口**（改动作下拉 + 点重播按钮），不要在探针里直接调
    `motionManager.startMotion` —— 后者会绕过页面自己的装填逻辑，测出来的"没反应"是假阴性；
  ③ 拿一个不依赖回放的数当裁判：**"既亮着、又有算出来的顶点"的片数**随时间扫一遍，
    最低值 >0 就说明那一刻该部位真的在画。
- ⚠️ **自证的"排除集"不能和被检对象同一尺寸档**：上面那条判据之所以整整一轮没抓到这个问题，
  是因为它只比"两侧都真画出面积"的片，而"有面积"定成宽≥1 单位 —— 手、手指、饰品本来就在 1 单位以下，
  **等于把最容易出事的对象划进免检区**，报出来还是"423/423 上屏、中位差 0.039 ⇒ 通过"。
  小对象要么单独给阈值，要么强制逐片列名比对。
- ⚠️ **别在改完数组之后再比"改前 vs 改后"**：本项目 `overwrittenByCore` 这条自证在 `relight()`
  之后才比 `D.opacities` 与钉进去的值，而 `relight()` 就是把数组改回那个值 ⇒ **永远报 0**。
  `coreModel.update()` 一返回就先 `slice()` 快照再比。通用形状：**任何"core 有没有覆盖我的写入"的断言，
  取样点必须落在覆盖之后、重钉之前**。
- ⚠️ **单参数扫描台账只能提名，不能定案**：逐点扫"只动一个参数、其余留默认"得到的
  "参数 X 管这 34 片的显隐"，在有参数联动或多门叠乘的 moc3 上会把因果记到**错的参数**头上
  （实测扫描说 `Param25=0.5` 该把某片抬到 1，直播同一参数值下该片 `op=0`）。
  定案要拿直播同一帧的 `(op, 顶点非零数)` 对读。
- ⚠️ **「状态选择器」参数必须瞬切，不能让它们沿曲线插值**（2026-10-16 实测，症状＝"手突然消失 / 手势做错"）：
  模型里有一类参数是**状态选择器**（键集是少数几个离散状态，例：`{0, 0.3, 0.4, 0.5, 0.7}`），
  而动画曲线常把它**从一个状态线性滑到另一个**（实测某皮肤在 clip 中途出现 `0.29 / 0.46 / 0.53`
  这些**非键值**）。滑行期间的形状就是：旧变体淡出 → **哪个变体都不在**（"突然消失"）→ 新变体淡入
  （"又出现逐渐实体化的虚影"），且滑行段显示的是**错的变体**（"手势做错"）。
  游戏侧这类参数通常由**状态机直接给状态值**（用户看录屏的原话："手直接换"、**消失次数 == 切换次数**）⇒
  网页要把它**量化**成状态值（本项目 = `snapMidGate` 逐帧贴最近作者键）。
  **但只量化这类多状态参数**：两键长坡（`0 → 0.812` 这种单段 ramp）量化会变阶梯，
  正是用户报过的"高光/手势在坡中点突跳"。
  判据（先做、再改）：取该参数在 clip 里的**键值集合**——键数 ≥3 且都挤在窄区间 ⇒ 选择器（量化）；
  只有 2 个键 ⇒ 长坡（**别碰**）。
  ⚠️ **量化必须按"作者键的时间序"做，切点取「段中点」**——只拿这一段的两端、到**中点**才切。
  两个极端都试过并被否：① "贴最近键值"会把坡中间的值钉到本段不存在的状态（见下一条）；
  ② "保住上一个键、到下一个键才瞬切"会把旧状态**抱**过整条坡，观感是"部件僵在那儿"（用户原话：
  "我不是说一直保持那个手势啊，太恐怖了"）。⇒ 只取段两端 + 段中点切，两头都躲开。
  ⚠️ **再顺手记一条**：量化必须按"作者键的时间序"做，**不要"贴最近键值"**：
  后者会把坡中间的值钉到**本段过渡里压根不存在的**状态 —— 实测 `0.3→0.5` 的坡被钉成 `0.4`
  （`0.4` 是同一 clip 别处 t=3.8~5.5 的状态），用户看到的就是"手势做错、又没换手"。
  判 clip 当前时刻要用**库自己的动作秒**（队列条目的 `_stateTimeSeconds`），
  别用页面自算的时钟（无头里组起点可能没设上 ⇒ 读成"页面存活秒数" ⇒ 键表一路读到末尾）。
  ⚠️ 那个库时钟还与 clip 时刻差一个**常量提前量**（实测 ~0.12s）⇒ 把切点做成**可调常数**
  （本项目 `snapLead()`，默认 0.12），并留一个**页面侧 A/B 入口**（URL 参数 / `window.__<名字>`），
  这样"切得早/晚"这类问题由用户的眼睛在页面上直接定案，不用每轮改代码重部署。
  ⚠️ **副作用**：量化后"某参数在 N 毫秒内必须变过"这类**活性判据会失效**（值可以合法地钉在同一状态上，
  实测一条探针因此报假红灯）⇒ 探针的活性判据要换成**与钉值无关的量**（队列/模型时钟推进）。

- ⚠️ **取证通道别因为"疑似闭环"就摘掉；真要下线必须留下恢复锚点**（2026-10-16 实测）：

## 16. 「某片为什么看不见」：细扫 + 逐片瞬断 + 曲线独立算值对表（2026-10-13 实测）

**症状形状**：一族片在动作播放过程中**短暂**消失，而"相隔几秒取两拍"的差分报**什么都没变**。
两拍差分之所以失灵，是因为它问的是"有没有被关掉"，而真相往往是"**被淡到接近零**"——
开关式阈值（`op_bad ≤ 0.01`）会把它整条放过。三步把它变成可算的东西：

1. **把时间轴采密**：同一趟播放里按 ≤0.05s 跑一串时刻，每帧**同时**落 ①画布图 ②全量逐片台账
   （`op` / 顶点包围盒 / drawOrder / renderOrder / UV / maskCount）。
   ⚠️ 步长决定你会不会正好错过事件——两拍采样错过一次 0.2s 的淡变，就会得出"全 0"的假否证。
2. **找形状，不找最大值**：对每片算**瞬断深度** `min(左侧历史最高, 右侧未来最高) − 谷底`
   （O(n)：`max_{i<j}v[i]` 与 `max_{k>j}v[k]` 两个前缀/后缀最大即可）。
   ⚠️ **不要用"画布变化最大的那一对"**：动作尾段常有几百片同时重排，最大值必然落在尾段，与症状无关。
   同理，时序判据要先切掉尾段（参数钳死 + 全局重排不是有效样本），报告里给"全窗"与"重排前"两个深度。
3. **拿磁盘曲线独立算一遍再对表**：把疑似闸门参数在 motion3 里的 `Segments` 插值出同一串时刻的值，
   与无头实测的 `op` 序列逐帧比。**吻合（实测 ≤0.04）才算钉住**，只"相关"不算。
   这一步把结论从"这几片好像变暗了"升级成一条可复算的等式（实例：`X族 op = 1 − Param75`，
   闸门是 clip 自己的 0↔1 方波，15.50 触顶 ⇒ 整族淡到 0）。
   ⚠️ motion3 **v3** 的曲线是 `{"Target","Id","Segments"}`，**没有 `Groups[].Name`**——
   按 `Groups` 取名字会静默拿到 `None`/`?`，看起来"这条动作没有该曲线"（本项目就这么漏看过一次）。
   ⚠️ **等式成立 ≠ 身份成立**：定量对表钉住的是"**这片为什么变暗**"，不是"**这片是什么**"。
   本例的等式（`X族 op = 1 − Param75`）复核全对，但"X 就是那只手"随后被用户交来的**游戏录像**否证——
   源数据是逐键对账过的，游戏在同一刻也会把它关掉，所以关掉的那套**不可能是**观众看见的那只手。
   ⇒ 把"某族变暗"当成症状之因之前，先问一句：**游戏里同一刻它灭不灭？** 一条外部真值能省掉整轮。
   另一条同向的自查：**换一条动作看它会不会离谱地脉动**（本例改播 `idle` 后该族 0.99→0.11→0.97，
   手不可能跟呼吸这么闪 ⇒ 那是个装饰/光效层）。

**与 §13（snap 钉互斥开关）的边界**：snap 治的是**跨 clip** 时交叉淡化把互斥开关参数插值穿过
"两套全灭"的死区。⚠️ 它管不到**同一条 clip 内部**作者自己把闸门参数拉到全灭值的情形——
那种暗窗发生在播放中途，`currentGroup` 从没变过，钉边界值的逻辑一次都不会触发。
所以"扩覆盖面"对这类症状是死路，先分清暗窗发生在**换动作那一下**还是**动作中途**。

**探针自身会骗人的六条**（都真实踩过）：

- `startMotion` 是**排队**：点完立刻读 `motionManager.state.currentGroup` 还是上一条 ⇒
  要推 ~0.36s 时钟再读，否则会把**正在播**的一趟判成"没起播"。
- **会话内重播可能"组切了、曲线不写"**：第二遍 `currentGroup` 正确但参数恒为默认值 ⇒
  任何"同会话跑两遍"的对照必须先验真、且比对两遍的**参数轨迹**，不一致就整趟作废（别去比像素）。
- CDP `eval` 一个箭头函数**表达式**必须带 `()`：否则返回函数对象，`returnByValue` 把它序列化成 `{}`，
  表现为"每帧都失败"而毫无异常。
- `toDataURL` 前必须先 `app.render()`（WebGL 默认不保留绘制缓冲）。
- **合成画布不能做绝对色判据**：页面环境光会把画面压成近灰（实测暖色像素只占 0.3%，且 ambient 随时间变）
  ⇒ 绝对阈值的"肤色/金色占比"列在这条管线上不可信。
- 无头与直播之间可能有一层状态没对齐（实例：某片直播恒 1.00、无头恒 0.00）
  ⇒ 逐片**绝对亮度**读数打折，方向性/时序性结论不受影响。

**按颜色认"哪一片是某件饰品"要带三重对照**（否则否证是假的）：① **贴片实心度**
（不透明像素 / UV 包围盒面积）——只量"金色占比"会把**发光点**判成金饰（外圈 alpha=0 被显示成白，
不透明像素反而 100% 饱和）；② 排掉**退化片**（顶点塌成一个点的画不出东西，却可能 op=1）；
③ 颜色序必须 `R≥G`，否则 `(180,255,97)` 这种绿会当金色过。并且必须打印**筛选漏斗**
（各级剩多少 + 不设门槛的 Top10 + 被哪级卡掉），"0 候选"才许引用。

**给运行时打补丁的两条硬规矩（§141 实测）**：

- **别指望从 `motionManager.definitions` 读曲线**：pixi-live2d-display 0.4.0 里
  `definitions[group][0]` 的键**只有 `["File"]`**（一个路径引用），曲线不在里面。
  要"作者写过哪些键值"，就按那个 `File` 自己 fetch `*.motion3.json` 解析 `Curves`，
  或用"连续 ≥3 帧不变的值"在运行时学出停靠值。
- **每帧改参数的补丁必须自带"我取到了几条数据"的钩子**。本轮 v1 就是这样被抓出来的：
  跑完参数照样走插值，真因是 `__snapStairDbg()` 报 **`n:0` —— 整层空转**。
  ⚠️ **空转的补丁比没补丁更糟**：下一轮会以为"这条路已经试过、没用"。
  验证第一步读钩子的计数，**不是**读画面、也不是读参数轨迹。
- 配套：改完正本先跑部署脚本再 `--check` 才能开始验证 —— 编辑器原子保存会断硬链，
  否则测的是旧副本（本轮差点把一次断链状态下的空测当验证结果）。

## 17. 同一 motion 内开关穿越淡变带：按作者键阶梯回贴（motion3 fetch）

**适用条件**：某些 ArtMesh 的不透明度只被 snapswitch 参数门控；动作本身把该参数从作者键 A 淡到作者键 B，中途插值让美术进入半透明。原来的 snap 只在跨 clip 时执行，捕不到同一 clip 的中途穿越。

**实现顺序**：
1. 不从 `motionManager.definitions[group][i]` 读曲线——其内容可能只有 `{File}`。按当前 group/index 取 `File`，页面 fetch 对应 motion3。
2. 复用唯一的 `curveId()` / `motionSegs()` 解析 `Target=Parameter`。作者键是首点及每段终点；对 snapswitch 白名单参数去重、数值排序。
3. **不要把整张 snapswitch 表一概逐帧阶梯化**。先选出与目标部件淡变有因果证据的参数/时间段，再限缩到该组回写；`snapswitch` 的“开关候选”是跨 clip 过渡安全的分类，并不证明该参数在每条 clip 内的每个作者键过渡都该瞬切。跨 clip 的 hold 参数必须优先跳过；其余姿态参数不得写。载入 promise 按 group/index 缓存，起播就预取，并提供调试钩子报告 file、曲线数、开关曲线数、作者键数和真实写入计数。
4. 无头验收必须先等“当前 motion3 已解析”，再检查目标部件的连续 op；同一条 clip 的 A/B 要配 `snapOff` 反向对照，确认关补丁能复现、开补丁能消除，并要求样本数量完整。只看到请求成功不等于解析/回写已生效。

**判据与限制**：目标 5 片至少 21 帧采样，关闭态应出现 `0.15 < op < 0.85` 阳性帧，启用态应归零；同时断言改动只触及明确列出的 snapswitch 参数集合。另须检查每个纳入参数的 motion3 键间跨度和作者段时长：若曲线本身是长坡，最近键会在两个端点之间点差处制造新跳变。gezi_2 `home` 的 GL1/4/5/7/8/9/10/11/12/14 各只有 0 与 18.25s 两个端点，整段连续斜坡；通用最近键法会让它们约在 9.125s 同时翻端点，符合身/臂高光突切的副作用。`Param25`/`Param27` 的多值过渡也会改为阶梯，可能改变中间手势时机。应对逐参数/逐转场做 A/B，并把“消除半透明”与“手势时序/其它高光保持正确”分开验收。两次独立 headless 的名义动作秒可能有启动偏移，姿态轨迹必须先用未改动参数/权威曲线锁相，不能直接按名义秒逐帧比较，也不能把未锁相结果写成“姿态完全相同”。

**涉及文件**：`gallery_src/index.html`（产品回写逻辑与诊断钩子）、`scripts/diag/l2d_wrist_ledger.py`（同 UI 入口采样、开关 A/B 与空转闸门）、相关根因记录写 `docs/TROUBLESHOOTING.md` 对应条目。改正本后先部署，再 `deploy_gallery.py --check`，之后才允许引用页面结果。


## 18. 倍速 / 时间缩放：动作时钟吃的是 `update()` 的**第二个参数**（2026-10-16 实测）

**需求形状**：给播放器加 0.1×–2× 倍速滑杆（或任何"让动作快/慢下来"的改动）。

**先查清库的时钟，再动手**。pixi-live2d-display 0.4.0（cubism4）的链条是：
```
onTickerUpdate(){ this.update(Ticker.shared.deltaMS) }      // Live2DModel：只做累加
update(t){ this.deltaTime+=t; this.elapsedTime+=t }          // 两个累加器
_render(){ this.deltaTime && (this.internalModel.update(this.deltaTime, this.elapsedTime), this.deltaTime=0) }
Cubism4InternalModel.update(t,e){ super.update(t,e); t/=1e3; e/=1e3;
  this.motionManager.update(this.coreModel, e) }              // ← 动作时钟 = **e（绝对时间）**
```

- **缩放 dt（第一个参数）对动作完全无效** —— 实测包住 `im.update` 把 `a[0]*=2`，
  用长坡参数当尺子量出来仍是 **1.02×**。dt 只喂物理/眨眼那几条。
- 库里**没有** `speed` 属性（整包 `grep -c speed` = 0），别去猜这个入口。
- **正解 = 自建虚拟时钟**：把「缩放后的 dt」和「自己累出来的绝对时间」一起喂回去：
  `im.update=function(dt,el){ const d=dt*k; vEl+=d; return orig(d, vEl); }`。
  虚拟钟从 0 起算没问题（管理器只吃差值，起播起点也来自同一条钟）；
  `autoUpdate=false`（暂停）时 `update()` 不被调用 ⇒ 虚拟钟也不走，**恢复不跳**。
- **范围要说清**：页面自己的外挂层（环境层/残留复位/开关钉住）若按 `performance.now()` 计时，
  它们**不随倍速变**。这是设计选择（环境层在源包里本就是独立 loop），但必须在注释与文档里写明，
  否则下一轮会被当成漏改。

**验收必须用比值，不能用绝对速率**：无头 swiftshader 下渲染慢，PIXI ticker 把 `deltaMS`
钳在 100ms（`_maxElapsedMS`）⇒ 模型时钟本来就只按墙钟的 ~0.6 倍推进（实测 1× = 0.59）。
钳位对各倍速一视同仁，所以：① 量 `vEl` 斜率之比 ≈ 倍速；② 量一个**离散事件**——
`Meta.Loop=false` 的整条动作「播完」那一刻的虚拟秒（1× 应当正好≈ clip 时长）。

**⚠️ 别拿"某个参数的轨迹"当时间尺子**（本页实测否证）：`GL1` 在 motion3 里只有首末两个作者键、
看着是天赐的线性斜坡，但它的**活值不是原始曲线** —— 用它反推时间，clip/虚拟钟 偏 **2.83 倍**，
把环境层关掉（`__ambOff`）反而偏到 **4.12 倍**。⇒ 凡是要用参数轨迹反推时间的判据，
**先证它的活值真的跟曲线走**（同一页里可能有别的写入者/插值路径）。
同理，**墙钟比值也不能断言 2.0**：无头停帧对 2× 的伤害比 1× 小，比值会被压扁（实测 1.46），
只可作方向性断言。

**探针自身的两个坑**：① 别靠"每趟之间等参数回落到起点"来重置（重播是从上一条动作淡过来的，
不等就两段门槛在同一拍一起越过 → 测得 0，探针还除零崩过）⇒ 判据要选**与重播无关**的量；
② CDP 在页面导航时会 `Execution context was destroyed`，要退避重试，别当成产品失败。

**配套**：给页面留一个 `window.__speedDbg=()=>({speed, vEl, real})` 钩子 —— 它把
"我的钟没按倍速走"和"库不吃这个时间参数"两种完全不同的失败分开，省掉一轮盲猜。

## 19. 重播 / 连点同一部位：`reserve()` 拒绝 × snapPending 误钉（2026-10-16 实测）

**需求形状**：播放中连点同一部位 / 点重播键，期望"立刻从头重播"，实际动作原地不动
（只重播语音）；或重播后出现"手势短暂错误 / 手消失一闪"。

**两条独立机制，先分清再修**：

1. **`reserve()` 拒绝"正在播的同一组"**：pixi-live2d-display 的 MotionManager 在
   `reserve(t,e,i)` 里 `if(t===this.currentGroup&&e===this.currentIndex) return false`
   （"Motion is already playing"）→ `startMotion` 直接返回 `ok=false`，**不真正起播**。
   `startMotion` 还是 async 的（`yield loadMotion` 之后才走 `state.start()`），
   拒绝发生在早于任何起播动作的位置。
2. **重播键要自走 `stopAllMotions()`**：先 `mm.stopAllMotions()`（内部 `_stopAllMotions()`
   + `state.reset()` 清掉 currentGroup/currentIndex）再 `play(sel)`，reserve 才不会拒绝。
   只重新走 `startMotion` 会被库拦下，看起来就是"只有语音重播、动作不重播"。

**核心坑：把"起播"记错的置位点**。包装器若无条件在自己开头置 `snapPending=true`（本页体系里
"下个 beforeMotionUpdate 执行某次钉值/回贴"的标志），reserve 拒绝时实际**不会**重新起播，
但标志已经置上 ⇒ 后续 beforeMotionUpdate 误判"动作变了" ⇒ snapHold 把**正在播的**动作的
关键参数（如手上 Param27/25）钉回 clip 起点值约 2 秒 ⇒ 手势短暂错误 + 手消失一闪。
**修法**：置位点必须移入对 `_startMotion` 的重写（真正走到起播才置），包装器只保留预载。
判据：连点后 `__snapDbg().held` 必须恒空。

**无头判据的落点（本页第 4 条重播类教训）**：判据必须落在**机制本身**——队列 entry 的
`_startTimeSeconds` / `_stateTimeSeconds`（点重播后 startTime 重置＝新起播、stateTime 继续涨）、
以及 snapHold 的 held 状态；**不能拿"参数值 ≠ clip 起点"当"动作中段"的标志**（gezi_2 的 home
曲线 Param27 有长时间 0.7 平台段，无头永远等不到"离开起点" ⇒ 探针误报 FAIL）。

**倍速键顺手规则**：倍速切换后用户想立刻回 1× 是高频动作——倍速标签本身做成可点
（title 提示"点一下回到 1×"），点击即 `setSpeed(1)`。
