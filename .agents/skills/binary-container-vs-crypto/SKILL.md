# 未知二进制载荷：加密 vs 自定义格式

## 何时用

手上有一类**能读到字节、但没有任何解析器认得**的载荷（游戏配置包、私有资源容器、被"加固"过的包），
需要回答一个二选一的问题：**它需要密钥，还是只需要读懂格式？** 这两条路成本差一个数量级，
判错方向会烧掉整天，所以必须先做本流程再动手。

**不适用**：已知格式的字段语义问题（直接读规范）；纯压缩率/编码问题。

## 核心纪律（本技能的全部价值在这一节）

1. **任何"正信号"必须配零假设**。裸比较"实测 X% vs 随机 1/X%"是错的：真实数据往往**既非随机也非加密**，
   而是"各文件独立、但共享同一套字节分布"。此时两两相等率的预测值 = **该分布自身的 IC**，
   不是 1/256。实测值落在 IC 附近 = 巧合，不是共密钥流。
2. **已知明文必须逐样本自撞**。拿 A 样本的词表去撞 B 样本，0 命中**不说明任何问题**
   （词表与内容本来不同源）。只有"用这个样本自己的已知明文撞这个样本"的结果才算证据。
3. **命中 0 也要有阴性对照**。判死一条假设时，同时跑一个"必然应该 0"的对照组
   （例如拿别的样本词表、或拿随机数据）。对照组也 0 → 说明测试本身没有区分力，结论要降级为"未验证"。
4. **不许用"看起来像明文"宣布成功**。必须预先写下唯一验收判据（与某个权威基准**逐字段一致**），
   并把它写进文档顶部。
5. **取不到的数字就不写**。文档里每个指标都要能指出它是哪条命令产出的。

## 管线（按成本从低到高，每步都给判据）

### 第 0 步：素材清点（最容易被跳过、回报最高）

先确认**盘上是否已有现成产物**，再决定要不要下载/跑工具：

```bash
ls -la <项目>/.diag/*/dump/ 2>/dev/null      # dumper 产物是否已经跑过
find . -maxdepth 3 -name '*.json' -newer <某基准> | head   # 已知明文基准在哪
```

实测教训：某项目上一轮把"跑 Il2CppDumper"记成待办并担心网络被墙，
而 `.diag/.../dump/` 里早就躺着 `dump.cs`（含每个方法的 RVA/Offset）、`stringliteral.json`、`DummyDll/`——
白绕了一整轮。**先查盘，再动手。**

同时核对**上一轮"线索"的归属**：从符号表/字符串堆里捞到的名字（`XorShift64`、`ctXor`、`Decrypt*`）
极可能是第三方库符号。判法：看它在符号转储里的**同上下文邻居**——

```bash
grep -n "XorShift64" dump.cs        # 邻居是 Mul128Fold64/Avalanche/rrmxmx → xxHash3，假线索
grep -n "ctXor" dump.cs            # public const ClipType ctXor = 3 → 几何库枚举，假线索
```

### 第 1 步：结构三查（几分钟，直接决定"要不要密钥"）

```python
# 1a. 重复块：加密/压缩流不可能有大量重复块
c = collections.Counter(b[i*16:(i+1)*16] for i in range(len(b)//16))
rep = sum(v-1 for v in c.values() if v > 1)
# 1b. lag 自相关（共密钥流/周期结构的判据）：对 d=1..64 统计 (C[i]^C[i+d])==0 的比例
#     真周期结构表现为 d 的**倍频系列**（3,6,9,12 依次衰减），不是单点
# 1c. 字节直方图 + IC + 熵
```

**判据**：

| 观测 | 结论 |
|---|---|
| 单文件内 16B 块重复数百次（iid 期望 ~1e-6） | **不是整体加密也不是整体压缩**；是记录流。转"读格式"路线 |
| 某标记串在文件里出现 N 次，且 N × 平均间隔 ≈ 文件长度 | 该标记是**每条记录的常量段**（不是文件尾魔数！），N ≈ 行数 |
| 头部按 LE32 能读出递增的行号/列号、第二字节缓慢递减 | 明文索引区，直接按记录解析 |
| 熵 ≥7.95 且无重复块 | 才需要往加密/压缩走 |

⚠️ 常见误读：把"文件尾 N 字节全表相同"当成"Footer 魔数"。先看它在**文件内部**出现多少次。

### 第 2 步：已知明文自撞（带阴性对照）

对**每个有权威基准的样本**，用它自己的词表，多编码撞：UTF-8 / UTF-16LE / UTF-16BE / GBK，
外加整条流的 1..7 位移位。没有基准的样本只能撞"领域高频词"（如中文台词必现词），
且结论要标注"无基准，弱证据"。

### 第 3 步：差分签名——一次判死"段内恒定密钥"整类

若 `C[i] = P[i] ⊙ K`（⊙ ∈ {xor,+,−}）且 K 在**一段内恒定**（哪怕每条记录换一个 K），
相邻字节的差分里 K 会完全抵消：`C[i]^C[i+1] == P[t]^P[t+1]`。
于是把整条流的相邻差分拼成一个"差分视图"，直接 `bytes.find(明文的差分)`：

```python
A = (np.frombuffer(C, np.uint8)[1:] ^ np.frombuffer(C, np.uint8)[:-1]).tobytes()
d = (np.frombuffer(P, np.uint8)[1:] ^ np.frombuffer(P, np.uint8)[:-1]).tobytes()   # len(d)>=4 才算
hit = A.find(d)
```

三种视图（xor / add / sub）+ 两种步长（lag1 / lag2）各跑一遍。
**盲区必须知道**：本测试对**短周期密钥**（K 每字节都在换）不敏感 → 必须接第 4 步。

### 第 4 步：周期攻击（用明文的结构约束，不需要已知明文）

短周期 XOR 会让第 3 步失效，但**明文自身的结构约束**可以反过来求解。
UTF-8 汉字的三字节区间是确定的（首字节 `E4..E9`、续字节 `80..BF`），
于是"每残差类该落在哪个区间"已知 → **逐类独立取 argmax** 就是可分优化，256×p 次计数：

```python
for r in range(p):
    col = np.frombuffer(body[r::p], np.uint8)
    k = max(range(256), key=lambda k: ((col ^ k) >= lo).sum() - ...)   # 落进期望区间的计数最大
```

**判据**：解出密钥后必须 (a) 合法三元组率大幅上升（真汉字文本应 ≥0.2，噪声只到 ~0.01）**且**
(b) 真的撞出已知明文串。只有 (a) 不算破口。

### 第 5 步：按记录边界试解压

上一轮若只在"文件偏移 0..63"试过 zlib/deflate/lz4/bz2，**那不算试过压缩**：
逐记录压缩的流起点在**记录边界**上（用第 1 步量出的标记偏移集合）。
每个边界 ±4/±8 各试一遍，并把"前 2/4 字节当小端长度前缀"的约定也试。

### 第 6 步：读真实代码，别再猜算法

统计路线到此为止。要么拿到解析器代码，要么拿到密钥——两者都在二进制里：

- IL2CPP：`dump.cs` 给出每个方法的 `RVA/Offset` → 用 **capstone** 直接反汇编 `Offset` 处的字节。
  先核对 ELF 头：`e_machine=0x3E` 是 **x86-64**（模拟器/PC 产物，本机 objdump 可用），
  `0xB7` 才是 AArch64。**函数起始地址非 4 字节对齐在 x86 上是正常的**，别当成"头被改过"。
- 找"收口函数"：从**调用链**上找唯一的 `byte[] → byte[]` 变换
  （`ReadAllBytes` 之类往往只是 `File.ReadAllBytes` 的薄封装，不是解密器）。
- **注意 `RuntimeHelpers.InitializeArray`**：方法体里出现它，说明那个 `byte[]` 常量
  **不在 so 的立即数里，而在 metadata 的 fieldDefaultValues 堆**里；
  此时"搜连续字节串"必然失败，得先把索引法解对（v31 的 stride 可用 `size % 8/12/16` 整除性自证，
  但**索引语义要单独验证**：`0x80xxxxxx` 形态的值是 **FIELD 元数据 token**，不是条目下标）。
- 用**已知明文反推密钥**往往比解索引便宜：如容器头 12 字节固定（`UnityFS` 签名）时，
  若变换是纯周期 XOR，`K[0..11] = C[0..11] ^ 那 12 字节` 直接可算。

### 第 7 步：设备与内存旁路（判定"能不能不破解就拿明文"）

顺序很重要，先便宜后贵：

1. `adb devices` + `tasklist` 确认模拟器/进程真的在跑（**别先启动重型环境**）。
2. **看 fd 表**：`su -c "ls -l /proc/<pid>/fd"`。若配置文件的 fd 直接指向原始目录，
   说明**没有解密缓存**，"捞现成明文"这条路当场封死。再配 `find / -xdev -iname '*conf*'` 兜底。
3. 内存取证只在前面都失败后做，且**全程只读**：只 `cat /proc/<pid>/maps` 与
   `dd if=/proc/<pid>/mem`，不 push、不写设备、不 attach 调试器、不暂停进程。

## 踩坑记录（都是真实踩过的）

- **`adb shell` 不能传二进制**：它会把 `\n` 改写成 `\r\n`（实测请求 262144 字节回 266643）。
  必须用 `adb exec-out`。并且**必须做逐字节阳性对照**：取一个本地已有文件的
  `off==0` 映射区前 4KB，与本地文件比对，不等就禁止宣布任何命中。
- **`adb shell su -c pidof X` 会静默返回空**：设备侧 sh 把 `X` 当成 `$0`，`pidof` 收到 0 个参数。
  必须整条命令带引号当一个参数传：`adb shell 'su -c "pidof X"'`。用 Python `subprocess` 传单个字符串最稳。
- **`/proc/<pid>/maps` 正则漏 `inode` 字段** → pathname 组拿到的是 inode，
  结果**所有区域都被误判成匿名区**，dump 范围算错。格式是
  `start-end perms offset dev inode pathname`，七个字段。
- **把第三方库符号名当解密器**（`XorShift64`→xxHash3、`ctXor`→ClipperLib、`Decrypt*`→CRIWARE 音频）。
  第 0 步的同上下文邻居检查 30 秒就能排除。
- **阈值定松 + 无对照 = 自己给自己发绿灯**：把"两两 XOR 零率 1.84% vs 随机 0.391%"判成"存在共密钥流"，
  实际零假设预测值是 1.904%。这是"假绿灯"家族里最隐蔽的一种，因为它有数字、看起来很像判据。
- **词表跨样本误用**（见核心纪律 2）。
- **只在文件头 0..63 试过压缩就宣布"非压缩"**（见第 5 步）。

## 交付与落档

- 探针脚本按编号入库（`01_`、`02_`…），**不放临时目录**；大件中间产物（明文候选、dumper 输出、内存快照）
  进 gitignore 区，文档里只留**结论 + 判据 + 涉及文件**。
- 每条被排除的假设写进"已排除的假设"表：`假设 | 判据 | 结果` 三列，**否证结论同样必须入库**，
  否则下个会话会原样重跑一遍。
- 唯一验收判据写在文档顶部，任何"疑似破解"都要立刻拿它自证。
