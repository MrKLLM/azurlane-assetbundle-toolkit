# 项目文档治理与状态文档瘦身

一套「先治本、再搬家、零丢失」的文档治理管线。核心洞察：状态文档膨胀的根因几乎总是**规范未覆盖全部文档类型**，导致每次会话只能往主文档里追加流水。只瘦身不改规范 = 下次还会膨胀。

## 适用症状

- 跨会话对接用的状态文档（PROJECT_STATUS.md / STATUS.md 等）膨胀到数百上千行，每次加载吃大量 token
- 文档里混着三种职责：当前进度快照 + 逐日会话流水 + 已解决 bug 的长篇排查
- 出现「自我作废」内容：新章节宣告取代旧章节，但旧章节整段还留着
- docs/ 目录文件数超过规则文档定义的分工，存在命名误导（如 DRAFT 实为审计报告）、拼写错误、内容重叠
- 用户明确要求「先更新规范文档，不然以后还会往同一个文件夹里加」

## 核心原则

1. **治本先于治标**：先改规则文档（路由表+红线），再动内容。顺序不可颠倒。
2. **归档不删除**：被取代的内容逐字外迁到 archive，主文档只留精炼版。任何精简动作必须保证信息零丢失。
3. **git mv 保历史**：文件迁移/改名一律 `git mv`，禁止普通 `mv`（会丢 rename 追踪）。
4. **先确认后执行**：改动文档、挪动大量内容前，先输出「现状诊断表 + 分步方案」待用户确认（本技能源自对此类约定项目的实践）。
5. **不动全局 git 配置**：提交用 `git -c user.name=... -c user.email=...` 单命令内联身份。
6. **瘦身有收敛点；到了就停手改规则，别再外迁**（2026-10-10 两轮实测）：第一轮通常能砍掉大半（实测 535→450，
   101 行是重复的过程流水），**第二轮往往只省十几行**（451→435，净 -16）——因为复印件已经搬完，
   剩下的重量是「未闭环事项 + 模块数 + 对接须知」这三样本身。此时继续外迁动的就是**交接状态**
   （要么砍掉桩里的闸门命令/待拍板项，要么把未闭环项整体搬去第二个文件、破坏"新会话只读一份就上手"）。
   ⇒ 判定收敛点的办法：按节量一次体量，标出其中 ⏳/⛔（未闭环）占的行数；
   若「未闭环现场」已占该节一半以上，就**别再搬**。
   超线的余量这时要用规则解决，两个方向按代价选：
   **A 分节预算**（各节各设上限，总量只是结果——适合"某一节天然会膨胀"的项目）；
   **B 装强制闸**（pre-commit 数行数并拦下，配一条带理由的绕行环境变量——适合"红线只是没人遵守"的项目）。
   多数项目的真相是 B：红线数字本身没错，**它烂掉是因为没有执行机制**（实测能从 399 涨到 534 而无任何报错）。
   两条都要比"抬阈值"好——抬阈值等于给放错位置发许可证。
7. **除按字符量找肥条目，还要找「同一结论的两个归属」**：路由表写的是"每类内容有且只有一个归属文件"，
   但同一次修复常被同时在两处叙述（实测：一处机制说明里 8 行引文块与"根因清单"第 7 条是同一件事，都指同一条 §）。
   这类重复不是放错位置，是**写入时没落实路由**——合并到归属地、另一处只留一行指针。

## 工作流

### Step 0 — 只读诊断（不写任何文件）

```bash
git ls-files docs/            # 确认哪些文档在跟踪中（决定能否 git mv）
wc -l docs/*.md *.md          # 行数/体量盘点
```

1. 读规则文档（AGENTS.md / CONTRIBUTING.md）中现有的文档分工约定。
2. 逐一对照实际 docs/ 文件，输出诊断表：`| 文件 | 实际定位 | 问题 |`（重叠、误导命名、过期、未覆盖）。
3. 明确指出根因：「规范只规定了 N 个文件的分工，实际有 M 个」——缺路由表才会持续乱加。
4. 给出后续三步方案（规范→目录→瘦身）+ 提交步骤，**等用户确认后再执行**。

4b. **第二把尺子：按字符量定位，别只信 `wc -l`**（2026-10-10 实测）。行数红线会被一种写入习惯彻底绕过——
   后续轮次的流水**接在同一条目的上一个物理行的句尾**，条目数与行数都不变、字数翻倍。实测一份 534 行的状态文档里，
   最大的一块**只占 1 行却有 5,681 字**，按行数看它毫无威胁。诊断时先跑：

   ```bash
   # 按条目（行首为 `N. ` 的列表项）累加字符量与行数，排序
   awk '/^[0-9]+[.)] /{if(cur)printf "%6d %4d  %s\n",ch,ln,cur; cur=$1;ln=0;ch=0} cur{ln++;ch+=length($0)}
        END{if(cur)printf "%6d %4d  %s\n",ch,ln,cur}' DOC.md | sort -rn | head
   ```

   两种结论对应两种完全不同的处置：**"条目多"**（平均 2~4 行/条，各带指针）⇒ 结构健康，不该动阈值；
   **"少数条目肥"**（前 3~4 条吃掉 >50% 重量）⇒ 是若干条"活攻关的现场流水"混进了状态文档，
   处置是给它们各配一个**归档段 + 一条自足的桩**，而不是抬阈值。
   阈值本身可以先回答一句：它是**索引型文档的条目预算**，不是内容预算，随项目规模亚线性。

4c. **瘦身前必须先审计"归档闸门自己是不是好的"**（顺序性硬要求）。逐字外迁的无损性由工具的四条核对背书，
   而其中"基线 md5 比对"这类守卫有依赖写盘副作用而恒假/恒绿的先例（见陷阱节）。
   ⇒ 动手前 `grep` 工具源码确认它拿什么比、比较两侧是否归一化过行尾（Windows `core.autocrlf=true` 下
   工作树 CRLF 与 `git show` 的 blob LF **永远不可能逐字节相同**）。**闸门没被证明有效之前，不许用它的"已校验"标注背书删除动作。**

### Step 1 — 治本：更新规则文档

在规则文档写入两节（模板如下，按项目替换文件名/阈值）：

```markdown
## 文档写入路由（什么内容写进哪个文件）
**每类内容有且只有一个归属文件**，避免重复与膨胀：

| 内容类型 | 归属文件 | 写入方式 |
|---|---|---|
| 当前进度快照、各部分状态、接手须知、待办 | `PROJECT_STATUS.md` | 就地精简更新，**不追加**会话流水 |
| 可复用的操作流程 / 技术选型 / 步骤 | `docs/WORKFLOWS.md` | 按主题追加 |
| 具体问题 → 原因 → 解决方案（踩坑） | `docs/TROUBLESHOOTING.md` | 追加条目 |
| 运行错误流水 | `docs/ERRORS.log` | 追加 |
| 某个工具的使用说明 | `docs/tools/<工具>使用说明.md` | 就地更新 |
| 一次性审计报告、被取代的旧交接文档 | `docs/archive/` | 移入，文件名带日期 |

## 体量红线
- 状态文档超过约 **400 行**即触发归档：当次会话内把溢出内容移入 `docs/archive/`。
- 逐日会话记录、已解决 bug 的长篇分析、调参流水 → 必须外迁，禁止留在状态文档。
- 新会话对接只需读状态文档即可上手；任何"必须翻历史才知道"的内容都属于放错了地方。
```

### Step 2 — docs/ 分层（git mv 保历史）

目标布局：

```
docs/
  README.md              # 纯导航索引（路由说明，不复述工具细节）
  tools/                 # 各工具使用说明
  archive/               # 过期一次性内容，文件名带日期前缀
    2026-06-21_目录审计报告.md
  WORKFLOWS.md / TROUBLESHOOTING.md / ...   # 路由表指定的常青文件留顶层
```

1. 只迁移 `git ls-files` 里出现的文件；未跟踪文件（如被 gitignore 的 log）按路由表原位保留。
2. `mkdir -p docs/tools docs/archive` 后逐个 `git mv docs/旧名 docs/新路径/新名`；改名时**修正拼写错误、误导名称，并加日期前缀**。
3. 原 README 若与 tools/ 内容重复，重写为纯导航索引（工具细节交给 tools/）。

### Step 3 — 主文档瘦身（按行逐字抽取，零丢失）

1. **完整读一遍主文档**（不能只看开头），逐节标记：✅保留 / 🗜外迁归档（被新版取代的旧章节、会话流水、调参日志）/ ❌删除（仅限重复标题等纯编辑残留，且删除行也计入归档核对）。
2. **先归档、后重写**：从原始文件**一次性**抽取所有标记块。行号必须在重写前锁定——先改主文档会行号漂移。

```python
# extract_to_archive.py — 按行号逐字抽取（1-indexed，闭区间）
SRC = "PROJECT_STATUS.md"          # 必须是尚未修改的原文
BLOCKS = [(401, 480, "§6 攻关路线(v1已废)"), (900, 1250, "§9 会话流水")]
lines = open(SRC, encoding="utf-8").read().splitlines(keepends=True)
with open("docs/archive/2026-09-16_PROJECT_STATUS_v1归档.md", "w", encoding="utf-8") as f:
    f.write("# PROJECT_STATUS.md 外迁归档（逐字保留，勿编辑）\n\n")
    for a, b, title in BLOCKS:
        f.write(f"\n\n---\n\n<!-- {title} | 原第 {a}-{b} 行 -->\n\n")
        f.writelines(lines[a-1:b])
```

3. 重写主文档为固定骨架：`项目概览 → 各部分状态表 → 当前主线 → 接手须知 → 待办`；指向归档的引用写**实际存在的相对路径**。
4. **多块替换必须从后往前**：`for a,b in BLOCKS: new[a-1:b] = 替换文本` 按升序跑会级联错位——
   第一块缩短后，第二块的行号已经指向别处，实测一次把 §2.7/2.8/2.9 整节切掉。归档块可以升序抽（都取自未改动的原数组），
   **但写回主文档前必须 `sorted(key=-起始行)`**，且每块替换前 `assert` 首/尾行锚点。
5. **基线自证（瘦身后唯一的复核凭据）**：瘦身前内容写盘后就没了，核对「零丢失」要有可信基线——
   `基线 = git show HEAD:<主文档> + 本轮那几处单点替换的行数组`，再断言其 md5 等于**抽取脚本读入时记录的值**。
   对不上说明基线不可信，必须停手（本轮真撞上一次：级联错位后的文件被当成基线，核对全绿却仍是错的）。
   有了可信基线就能跑三条硬核对：① 基线每条非空行都能在「新主文档 + 归档」里查到；② 每个归档块与基线对应区间逐字相同；
   ③ 新主文档里的文件引用**不得比基线新增断链**——不是"绝对零断链"：长文档里的路径有两种根口径（仓库根相对
   `scripts/diag/x.py`、运行时目录相对 `CG_v2/foo.png` 实为 `Output/CG_v2/…`），按仓库根硬判零会把两条历史遗留变成常亮警报，
   而下一次真断链就混在里面没人看了。切片比对时按**标记位置**取块，别用正则前瞻——块间分隔符 `\n\n---\n\n`
   会被 `.*?` 连同下一块的注释头一起吃掉，表现是"只找到 3/5 块"。
6. 验证：

```bash
wc -l PROJECT_STATUS.md docs/archive/*_归档.md   # 主文档 ≤ 红线；归档行数 ≈ 被移出内容之和
git diff --numstat                                # 删除量集中在被标记章节；行尾没被归一（归一了会显示成整文件重写）
```

7. **搬整段前先查"这段的编号有没有被别处引用"**：`grep -rn "第 N 条" docs/ *.md`。有外部引用（`docs/name_review_*.md`
   里那种"§6 第 2 条原记…"）就**原位留一行桩、编号一律不动**——桩写"✅ + 一行结论 + 流水外迁 A{n} 段"。
   直接删段会让外部引用静默落到**另一条同号条目**上（编号列表里"第 2 条"仍然成立，所以四条核对全绿也抓不到）。
   同理，本轮**就地改写**的行（哪怕只是头部那行归档索引）也要另起一个 `A{n}b` 块留底，否则核对① 会报"缺失 2"、
   "零丢失"当场不成立。
8. **这套核对值得做成工具**，别每轮手写抽取脚本：`scripts/diag/doc_verbatim_archive.py`
   （清单 JSON 给 `[{lines:[a,b], stub}]` → 干跑打印计划 → `--apply` 落盘 → `--verify` 事后复核）。
   三态各自抓一种失效：干跑抓行号错位，`--apply` 前后各取一次 md5 与 `git show HEAD:` 比抓**并行会话插队**，
   `--verify` 断言"磁盘 == 基线 + 本次外迁应有的结果"抓**写完之后被人整文件写回**（那种 git 不报冲突）。

   ⚠️ **两条实测（2026-10-17，给 §6 加三条新待办时踩到）**：
   ① `base=HEAD` 要求主文档与基线**逐字节相同** ⇒ **一轮只允许 `--apply` 一次**：想搬的多段必须在**同一份清单里
   一次给全**（非连续行号可以多段并列）；搬完一段才想起第二段，就只能 `git checkout --` 主文档 + **删掉已写出的
   归档文件**再从 HEAD 重来（直接重跑会在同一归档文件里**重复追加**）。
   ② **别按字符数估新条目花多少字节**：本轮三条待办按字符估约 890 字节、**实测 1,654**（CJK ≈3 字节/字，
   `「」／——` 等全角标点同样 3 字节）⇒ 一写下去超线 639。正确顺序：**先量余量再写** ——
   `git cat-file -s :PROJECT_STATUS.md`（闸量的是**暂存区 LF blob**，工作树是 CRLF、比它多约「行数」字节）+ 预算 96,000；
   空间不够时第一步永远是**压自己刚写的文字**，不是动交接状态。

### Step 4 — 提交

```bash
git status && git add docs/ PROJECT_STATUS.md AGENTS.md   # 只 stage 文档相关变更，无关遗留不纳入
git -c user.name="Repo Author" -c user.email="repo@author.local" \
  commit -m "文档治理：AGENTS.md 加写入路由规范 + docs 目录分层 + PROJECT_STATUS 瘦身"
git log --stat -1 | grep -i "rename"   # 确认 rename 被识别（100% 相似度=历史保留）
git log --follow --oneline -3 docs/archive/2026-06-21_目录审计报告.md  # 抽查历史可追溯
```

commit message 用中文、匹配仓库既有风格；作者身份取仓库历史（`git log -1 --format='%an <%ae>'`），不改 git config。

## 验证清单

- [ ] 路由表覆盖了 `git ls-files` 中全部文档，无「无家可归」类型
- [ ] 主文档行数 ≤ 体量红线
- [ ] 归档行数 ≥ 被移出章节行数之和（抽查首尾各一块为逐字原文）
- [ ] 多块替换按**行号降序**写回，且每块首/尾行锚点 assert 过（防级联错位切错节）
- [ ] 基线 md5 == 抽取脚本读入时记录的值，然后才允许声称"零丢失"
- [ ] `git mv` 的文件用 `--follow` 能追溯到迁移前历史
- [ ] 主文档内所有文件引用/链接指向实际存在的路径
- [ ] 未 stage 与本任务无关的变更

## 陷阱

- **直接删除而非归档** → 信息永久丢失。任何"看起来没用了"的章节都走外迁，让 git 历史做最后兜底。
- **普通 `mv` 替代 `git mv`** → rename 无法被识别，历史断链。
- **先改主文档再抽取** → 行号漂移抽错内容。必须从原始文件一次性抽取完毕、核对后，才允许重写主文档。
- **一条破线拆成 N 次小归档** → 每次都重新对齐一次基线行号、每次都冒并行会话插队的风险。
  归档工具通常支持**一份清单装多段**（行区间不得重叠、均为 `git show HEAD:doc` 的 1-based 闭区间）
  ⇒ 干跑一次看总账、`--apply` 一次落盘、`--verify` 一次复核。**复核之后才允许手改主文档**
  （更新生成时间、就地标记完成），因为手改会让本次 manifest 的 `--verify` 从此刻失效。
  落盘后必查 `git diff --numstat`：应当是**局部**形状（如 `22  106`），出现上千行即行尾归一化把全文件重写了，回滚重来。
- **README 保留工具说明** → 与 tools/ 长期重复、双双过期。README 只做导航。
- **瘦身后忘改主文档里的归档引用** → 指向不存在路径的断链。
- **「假路径型」指针（比断链更坏，2026-10-10 实测一条）** → 桩里写「逐字见 A25 段」，那个文件**确实存在**，
  断链检查全绿，但里面**根本没有那些内容**（真身在另一份取证文档）。瘦身把主文档这份正本删掉之后，
  下一轮按指针去找 ⇒ 判定"证据丢了"、重跑几小时取证。
  ⇒ **每一条跨文件指针在依赖它之前要用 1~2 个特征串（数字 / 专名 / 报错原文）`grep -rl` 实测命中**；
  命不中就当唯一副本处理，并在桩里留下「旧指针勘误」一句话，防止后人再去原地翻。
- **归档=有 bytes，不等于找得到** → 归档文件堆到十几个、单个上百 KB，而目录里没有段号索引时，
  里面的内容实际不可达（本项目 `docs/archive/` 11 个文件曾长期无 README）。
  ⇒ **瘦身那一轮必须同时产出/更新 `docs/archive/README.md` 的「段号 → 文件 → 内容」查找表**，
  并把主文档头部那段逐年膨胀的外迁台账压成一行指向它。另注意：正文里的 `追加-I…XIII` 这类
  **行内加粗编号不是标题**，`grep '^#+.*追加'` 命中 0，只能按串 grep——这类"结构性不可检索"要写进索引。
- **留的桩只剩"已闭环，见归档"** → 下一会话为了拿判据/闸门命令必须翻归档，等于把红线压力搬了个地方。
  桩要自带**可执行结论**（闸门命令、判据数值、"别再攻"这类方向性裁定），流水部分才进归档。
- **只瘦身不改规范** → 下次会话继续往同一文件追加，膨胀复发。顺序必须：规范 → 目录 → 瘦身。
- **整块替换时吃掉了相邻定义的头部** → 用「整行 + 下一段头一行」当锚点插入时，old_string 覆盖到几行就会删掉几行：
  实测一次把 `def ship_voice_count(sh):` 连同其文档行一起替换掉，函数体挂在别的名字下、语法能过但运行时才炸。
  ⇒ **插入型改动 old_string 只允许命中"一行的完整文本"，新内容 = 原行 + 追加**；改完立刻 `compileall`（不能只看不跑）。
- **归档工具的两类"从没跑到过的路径"**（2026-10-05 实测各撞一次，都会让红线判据失真或当场崩）：
  ① 归档目标是**本轮新建文件**时，无条件 `open(archive).read()` 直接 `FileNotFoundError`——历史上都是
  往已存在的 A 段文件追加，所以这条分支从未执行过；新建时还要自带那份"逐字保留，勿编辑"的文件头。
  ② **桩（stub）可以是多行**，若把整串 stub 当成一个元素塞进行数组，`len()` 会少算 ⇒ 计划打印
  "预计 385 行 / 实际 401 行"，而 400 行红线正是拿这个数判的。⇒ 桩必须 `split(chr(10))` 展开后再计数。
- **逐字基线守卫拿"字节 md5"比 `git show` 与工作树** → 在 `core.autocrlf=true` 的 Windows 仓库里
  **恒假**（blob 存 LF、检出是 CRLF），于是外迁动作谁都做不了，而报错文本会把矛头指向一个
  并不存在的"并行会话刚落盘"（2026-10-10 实测：`git status` 干净、`git diff` 空，守卫照样中止）。
  ⇒ 守卫要守的是**内容**：两侧先 `replace(b'\r\n', b'\n')` 再比；**写回时保留工作树原本的行尾风格**
  （把 CRLF 文档整文件写成 LF 会在 diff 里炸出"全文件重写"噪声，也污染下一次逐字比对）；
  **四条核对读回时也要归一化**，否则每行尾部多一个 `\r` 会把"逐行可查"判成全丢——
  一个恒假的守卫换成一个恒红的核对等于没修。
- **"这条闸门以前跑成功过"不能证明它现在有效** → 它上一次通过可能靠的是**写盘副作用**：
  旧版工具自己把主文档写成 LF，于是紧接着再跑一次就是 LF vs LF 命中。任何人做一次
  `git checkout -- <file>`（恢复成检出形态 CRLF）就把它永久变成障碍。
  ⇒ 接手这类"防插队"守卫时，先在**什么都没发生**的状态下要求它绿，再问一句
  "它上一次通过，是因为内容真的没变，还是因为某个副作用"。
- **用未落盘的 `date` 填时间戳** → `> **生成时间**:` 写着未来 20 分钟，跨会话核对时一眼假。取时间要跟写盘在同一处完成。

- **用全局 git config 换身份提交** → 污染用户机器配置。用 `git -c` 内联。
- **`open(p,'w').write(open(p).read() + 追加)` 这一行式"追加"** → 表达式前半的写句柄**先把整份文件截断**，
  后半的 `read()` 读到空串 ⇒ 归档文件只剩刚追加的那几行。真实事故：一次把 583 行 / 10 个归档段的
  外迁档截成 9 行（靠 `git checkout --` 复原；A 段内容本身是 `git show HEAD:<主文档>` 的行区间，可重生成）。
  ⇒ ① 追加一律 `with open(p,'a')`；要"读旧+写新"就必须**先读进变量、再开写句柄**（分两句）。
  ② 重写整份长文档后**立刻** `wc -l` 并数一次归档段标记（`grep -c "<!-- A\d+"`），段数变少就是截断。
  ③ 动手前确认目标在 git 里——`.diag/` 这类 gitignore 目录用同一写法**不可逆**。

## 配套：决议落地审计（不属于上面四步）

治理动作跑完后，另一类会静默失效的东西是**上一轮的决议**——「这条要并进某技能 §9」「那个待办下次补」。
它们只存在于会话记录里，没人再核对，于是规则文档越来越长、执行率不变。

**判据**：审计结论必须落在盘上文件的字面证据（grep 出的行号、`version:` 字段值），不得落在「上轮说过要做」。

1. 把每条决议翻成**可 grep 的具体标记**：章节号（`§9`）、版本号（`v1.4.0`）、条目编号（`WF-22`）、小节标题原文。
   含糊描述（"补进 Live2D 那个技能"）无法核对，等于没写。
2. 只看结构标记，不要通读文件、也不要信决议本身的措辞：

```bash
grep -n "^## \|^### " .agents/skills/<目标技能>/SKILL.md | tail -6   # 章节只到 §8 ⇒ 承诺的 §9 没落地
grep -n "^version:"   .agents/skills/<目标技能>/SKILL.md              # 版本没变 ⇒ 那个文件没被改过
grep -rn "WF-22" docs/WORKFLOWS.md                                    # 编号类条目直接查在不在
```

3. 得出「没落地」前先排除**记错目标**：文件可能已改名/拆分/换编号约定（`§9` vs `9.` vs "第 9 节"），
   先 `ls` 确认对象存在，再确认编号约定没变——否则会把「换了写法」审成「没做」。
4. 补做后**当轮入库**（写进技能/文档并 commit），不要留在会话记录里；同时更新被改对象的 `version:` 末位，
   让下次审计能用版本号一眼看出改没改过。

**失效模式**

- 决议只写成自然语言承诺、无任何可核对标记 → 下一会话根本不知道它存在。
  真实案例：某轮把「动作语音层要并进 `live2d-web-runtime-integration` §9」记成决议，那个技能实际停在 §8、版本也没动，整轮无人发现。
- 拿「待办清单里有这一行」当「已落地」的证据 → 待办条目恰恰是**没做**的标记。
- 只审自己本轮做的动作，不审上一轮欠的 → 欠债永远往后传。收尾清单里应有一条「回查上轮承诺」。

想让它每轮都真发生，光写这段不够（规则在文档里 = 只在想起来时生效），要配硬约束：见技能 `enforce-project-rule-as-git-hook`。

## 配套：错标修复（专名/术语写错，禁止全局替换）

文档里的人名、代号、ID 写错时，"把错的换成对的"这个直觉是错的：**同一个错串可能在别处是对的**。
真实案例：dorm3d 全线把角色写成「天津风」，而 `tianjinfeng` 确实是一艘存在的船（皮肤「狐仙大人驾到」，
在立绘线被正确记录 21 处）；被写错的那 7 处其实是 `tianlangxing` = 天狼星。全局替换会当场改坏 21 条。

1. **先按语境过滤命中行**，再逐处判定归属，不得按字符串全量替换：
   `grep -n "<错串>" f` 拿到总数 N → 用**同行必然出现的语境词**（资产 key、目录名、章节号）筛出子集 →
   只改子集。判据 = 改完重跑同一条语境过滤，命中必须只剩"勘误注释自身"；并核对 `grep -c` 从 N 减到 N-k。
2. **名字必须回表取，并标来源档位**：专名的权威源是数据表（本项目 = `Output/ship_meta.json` 的 `cn`，
   其正本 `ship_data_statistics.name`），不是任何一份 md。直读到值的和按拼音/缩写推的要分档写明，
   否则下一会话会把推测当事实再传一轮。
3. **顺手钉口径**：同一数值若有两种单位（307 MB 十进制 vs 292.6 MiB）且历史文档混用，新写的表必须声明口径，
   并留一行说明旧数字属于哪种——否则"改错了"会被追回到一个从来没写错的数上。
4. **落盘后逐格回算**：用独立脚本从原始数据重算新表的每一格再比对（10 行 ×4 格全过才算验过）。
   表格写得好看 ≠ 数值对得上；这一步同时能抓出"我算错"和"源数据里有例外"（例：8 个角色里 1 个的
   贴图包是目录不是单包）。
