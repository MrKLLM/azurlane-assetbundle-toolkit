# Windows 硬链接去重 + 三重校验安全流程

把一批**逐字节相同**的重复文件转成 NTFS 硬链接：磁盘只存一份数据，但每个文件路径都还在、读出来字节一模一样。核心区别于「删重复文件」——画廊的 `index.json` / 静态站的 `<img src>` 是**按文件名引用**的，直接删会断链显示不出来；硬链接去重后原路径依然能正常读，前端一行都不用改。

正因为消费方按文件名引用，去重的**成败判据不是「省了多少」，而是「受影响路径经本地 http.server 仍能 200 打开、字节与哈希一致」**。本技能用可复跑的脚本把这条判据钉死。

## 何时使用

- 资产目录里有大量逐字节相同的重复文件（如 `npcX`==`X`、`_asmr`/`_hx` 变体==本体、三视图同图），想省磁盘但不能删。
- 磁盘被只读批量产物占满，重复率高。
- 用户明确要「硬链接去重」，并要求「去重后逐组校验画廊/网页能正常打开」。

## 不适用

- 需要跨卷/跨盘去重（硬链接只能在**同一分区/卷**内）。
- 文件内容会**各自独立**演化（两边要存不同东西）——硬链共享数据，改一个=改全部。只读归档资产天然满足；可编辑文件只有在"两边本该是同一份"时才适用，见下面「变体」。
- 只是想删文件腾空间、且消费方不依赖文件名（用普通回收站删除即可，无需本流程）。
- 近似重复（视觉相似但字节不同）——本技能只处理**逐字节相同**，不做感知哈希。

## 前置约定

- Python 3（`os.link` 在 Windows 上创建硬链接），需在同一 NTFS 卷内。
- 三个脚本在 `scripts/` 下，通过环境变量 `DEDUP_ROOT`（产物根目录）与 `.diag/_dedup_plan.json` 传递方案；按需改脚本顶部 `DIRS`（要扫描的子目录列表）与扩展名。
- 遵守「先只读出方案 → 小样本 → 用户确认 → 全量」的项目红线：未展示小样本结果前不得全量。

## 工作流（5 步）

### 0. 先判"这活该不该走硬链接去重"（只读，几分钟，决定后面做不做）

被问"这目录膨胀得厉害，能省多少"时，**先去重很可能是错的答案**。三个只读量法，缺一个都会给出错的数量级：

1. **嫌疑上限 ≠ 可回收**。按 `(size, nlink)` 分组的"同尺寸嫌疑"会**严重虚高**，必须走
   size 分组 → 首 1 MB 采样哈希 → 全文件哈希 三级，只有第三级的数字能写进结论。
   真实对照（2026-10-06，80 GB 级资产仓）：某音频目录嫌疑 **1.90 GB → 实证 0.09 GB（21 倍）**；
   源包目录嫌疑 **0.73 GB → 实证 0.00 GB / 0 组**（9.3 万个包两两互不相同，一个都链不动）。
   全仓实证重复 **1.3 GB = 1.5%** ⇒ 本轮结论就是"去重不是杠杆"，没有进入第 1 步。
2. **省空间的头名通常是"没人读的大产物导出"，不是重复**。找零引用大件：
   逐顶层目录量体量，再 grep 消费方（索引 js/json、前端源码），**引用 0 处**才算零引用。
   同一轮里 536 个 BGM wav 独占 **12.6 GB**、全库零消费方，而它可由仍在本地的源包确定性重导。
3. **备份类目录默认答案是"不删"**，且判据要用**完整相对路径**配对。
   按**文件名**把备份和线上配对会假阳性（跨模型/跨目录同名，实测 268 个"看起来相同"其实是不同文件）。
   ⚠️ 若产物目录整个被 `.gitignore` 掉，则 git 只兜得住脚本、兜不住字节 ——
   换入前那一版**只存在于备份目录里**，删掉即永久失去回滚点。
   这种目录里"整项可删"的判据是 **该项每个文件都与线上逐字节相同**（实证后 29 项中 0 项满足）。
   例外只有两种：空目录、以及"备份与线上全等 = 那次换入等于没改"。

判据：能一句话报出「实证可回收 X GB / 占总仓 Y%」且 X 不是从同尺寸上限来的，才决定走不走第 1 步；
结论是不走时，把上面三条的输出（体量表 + grep 引用 + 唯一副本审计）交给人拍板。

#### 0b. 删「看起来是旧副本」的整层资产：唯一性 ≠ 价值 ≠ 可再生（三层都要，顺序不能倒）

上面第 1/3 条回答的是"能不能链"，但当结论是"**删掉整个子目录**"时，同尺寸→md5 那套只证到
"盘上没有第二份"，**不证"这一份是产物"**。实测一次 87 件 / 80 MB 的清理，定性连翻两次：

- 按**文件名**在生产目录里找同名 ⇒ 一半文件"零命中"，看起来像"漏掉的资产"。**错**——旧管线用数字/内部 id 命名。
- 按**内容**（size 索引 → 同尺寸才 md5，忽略文件名）⇒ 只有 7 件是实证重复，其余 ~47 MB "唯一"，
  看起来更像"缺失的产物"。**还是错**。
- 决定性证据是**像素尺寸 + 权威表收录**：那批"唯一"文件是 **2048×620 的横条**和 **1024×580 的预览小图**
  （旧导出层里的附属件，不是成品大图）；同名成品在生产目录里尺寸大一倍（3894×3473 vs 2048×1266）；
  而它们在权威皮肤表里 **0 收录** ⇒ 准确说法是"新管线有意不收这一类"，不是"新管线漏了"。

⇒ 三层判据固定成：**① 内容级唯一性**（跨全部生产目录，忽略文件名）→ **② 唯一的那些是不是产物**
（量尺寸/与同名新产物比尺寸/查权威元数据表收不收录）→ **③ 可再生性**（源在不在盘上、重导**能否逐件复原**）。
第 ③ 层最容易漏：`png 张数 < 源包个数` 说明重导**不等于逐件复原**，所以**删前必须落一份逐件清单**
（name / bytes / md5 / 像素尺寸），否则"可再生"只是口头承诺。

顺带两条护栏：
- **补完一个旧脚本之前先 dry 比对它的目录前提**（列一遍它 `os.path.isdir` 的每个入口）。前提烂掉的脚本
  补完只会产出第二份错误副本，而它唯一真会执行的动作可能是往**生产目录**里复制垃圾。
- 删除脚本的路径护栏在 Windows 上会**自己 fail-closed**：`os.path.commonpath` 返回**反斜杠**形式，
  与正斜杠拼的根目录字符串 `!=` ⇒ assert 直接 abort（0 文件受损，这是正确行为）。
  护栏必须 `os.path.normpath()` 两侧后再比，且 abort 后**先确认没删再改**，别把 abort 当"已执行"。
本项目已把这三件事合成一个只读工具：`py -3 scripts/diag/check_disk_footprint.py [--confirm] [--bak-uniqueness] [--target <子树>]`
（`--confirm` 走两级哈希实证、`--bak-uniqueness` 逐份审计备份目录还剩几份独一无二；退出码 0 = 量完，结论交人判）。

### 1. 只读扫描，生成去重方案

跑 `scripts/dedup_plan.py`。它按 **size 分组 → 同尺寸算 sha256 → 组内真实字节比对确认逐字节相同 → 跳过已互为硬链（同 `st_ino`）→ 每组选一个 canonical**，输出 `.diag/_dedup_plan.json` 与人类汇总（组数 / 重复文件数 / 预估可省空间）。不落盘任何资产改动。

```
cd "<项目根>"
DEDUP_ROOT="Output" PYTHONIOENCODING=utf-8 py -3 scripts/dedup_plan.py
```

把汇总（尤其是重复对是否都是**真实冗余**）展示给用户确认后再进入第 2 步。

### 2. 小样本试链（1–3 组）

跑 `scripts/dedup_apply.py 2`（参数 = 前 N 组，或 `all`）。逐 dup 流程：**建链前再次真实字节复核 → `os.remove` + `os.link` → 失败自动回退 `copy` → 逐文件校验 `nlink≥2` + sha256 与 canonical 全等**。把已应用路径写进 `.diag/_dedup_applied.txt`。期望「N 文件建链、0 问题」。

### 3. 端到端 HTTP 校验（小样本）

跑 `scripts/dedup_httpverify.py`：进程内起 `ThreadingHTTPServer` 根于产物目录，GET `_dedup_applied.txt` 里每个受影响路径，核对 **HTTP 200 + Content-Length + 下载字节 sha256 三重一致**。这一步证明硬链文件经画廊的 http.server 能正常打开——是「画廊零破坏」的直接证据。期望 `x/x 全部通过`。

### 4. 全量应用 + 全量校验

确认后跑 `scripts/dedup_apply.py all`，再对**全部**受影响路径重跑第 3 步。

> 幂等性：`all` 会把小样本那几组再处理一遍。已链的 dup 此时 `st_nlink` 已 >1，`remove`+`link` 回来是无害的，`freed` 因测的是 nlink 增量而**不重复计**——所以全量实际释放会略低于「小样本+预估」之和，属正常，不是丢链。

### 5. 磁盘实占核对 + 记录

按 inode 去重统计各目录 **logical（Σsize）vs physical（Σsize/nlink）**，抽样确认 `nlink>1`，核对物理实省 ≈ 方案预估。更新项目状态文档（一行记录：组数/重复数/实省/校验通过）并提交。去重脚本可留在 `.diag`（或 `scripts/`）供产物更新时复用。

## 三重校验的含义（为什么缺一不可）

- **逐文件 `nlink≥2` + sha256**：证明硬链真的生效、且内容与 canonical 逐字节相同。
- **本地 http.server GET 200**：证明按文件名引用的消费方（画廊/静态站）仍能解析并打开该路径——这是「不删只链」相对「删重复」的核心优势。
- **Content-Length + 下载哈希一致**：证明服务端读出的是完整正确字节，没有因链接/编码问题被截断。

## 变体：手写正本 ↔ 运行目录副本（消掉"改了忘部署"）

批量去重之外，硬链还有一类高价值用法：**一个手写的正本（前端 html / 配置 / 脚本）被单向 copy 到某个运行目录**。这种结构天然带一个静默失败——改正本不部署则运行的是旧版；改运行副本则下次部署被无声覆盖。两边都是 nlink=1 的独立副本时，用户看到的就是"两份重复文件，还点不开"，进而想删掉正本。

**为什么硬链会断（先讲机制，否则"断链"听起来像随时会炸）**：数据本身没有名字，路径只是指向它的门牌，`nlink` 数的是"几个门牌"。程序存盘有两条路——**原地改**（打开那份数据写进去，门牌不动，所有路径同时看到新内容）与**写新的再换旧牌**（写 `_tmp` → 删旧门牌 → 把临时文件改名顶上去，即"原子保存"，崩溃时不留半截文件，VS Code / 多数编辑器 / 智能体的整文件写回都走这条）。后者会让这个门牌改指另一份数据，`nlink` 当场回 1，两边变回独立副本。**断链不丢任何数据、也不会让消费方读不到**，退化回来的只是"两份副本 + 忘部署"这个老问题——正因为它不痛，必须用非零退出的检查去拦，见第 5 步。

判据与步骤（与批量去重共用一套工具，只是规模是"几个文件"）：

1. **先证它是副本而不是引用**：`stat -c 'nlink=%h ino=%i'` 两边。`nlink=1` + inode 不同 = 两份真拷贝；inode 相同才本来就是一体。**别用 md5 相同来推断"是同一份"**——那恰恰是两份副本最像的时候。
2. **问清哪边是正本**：`git ls-files` 看哪条路径被跟踪。若运行目录整个在 `.gitignore` 里，删掉未被跟踪的"那份"就是删唯一版本；这种目录下"看着重复"的东西**默认不可删**。
3. **换链**：`os.remove(dst)` + `os.link(src, dst)`，随后 `--check` 式复核（同 inode + nlink≥2 + 逐字节）。换链前**必须两边逐字节相同**，否则拒绝——这是防止用换链偷偷覆盖掉一边的改动。
4. **并发闸门（共享工作树必配）**：换链前跑 `git diff --quiet HEAD -- <正本路径>`，**非 0（有未提交改动）就跳过该文件**。这条规则当场就能救命：另一个会话几分钟前刚写过、mtime 还热乎的文件，会被它自动排除在本次换链之外。
5. **配一个长期漂移探测器，且它的判据必须是结构性的**：把 copy 模式降级为"回退手段"，另加只读 `--check`，
   要求**清单里每个文件都必须仍同 inode**，任何一条退回 `nlink=1` 就非零退出——**不能只比内容**。
   真实教训：硬链上线 3 小时就被一次「整文件写回」断开，而当时 `--check` 只比 md5，于是打印
   "已一致（独立副本）" 后 `exit 0`，**对唯一会真实发生的失效模式给了绿灯**；断链当场不丢数据、
   消费方照常读，所以它天然不痛不痒，只能靠"该链的没链上 = 失败"这一条非零退出拦住。
   探测器消息要能分诊：全绿 / 断链未漂移（`--relink`）/ 断链且漂移（先 copy 刷平再 `--relink`）。
6. **别把护栏立在"我用了正确的改法"上**：原地编辑并不能防断链——多数编辑器、以及**智能体的 Edit/写文件工具**内部都是"写 `_tmp` → 改名顶上去"，2026-09-27 实测 Edit 改硬链正本后漂移检查当场报红。⇒ 唯一护栏是**收尾必跑那个结构性 `--check`**；红了按 **用正本刷平 → 提交 → 再补链 → 再查** 四步收，且"先提交"不能跳（补链那步会自动跳过正本有未提交改动的文件，那是它区分"别的会话正在写"的判据）。
   多智能体/多编辑器共用的仓库里，这条要写进项目规则文档——但写的是"**改完必查**"，不是"必须原地编辑"。

改完之后必测的三件事：① 写入穿透（改正本 → 另一路径立刻读到新内容，测完按原字节还原并核对 `git diff HEAD` 干净）；② `--check` 在人为造漂移时**必须报红并非零退出**（不测失败分支的探测器等于假绿灯）；③ 消费方仍按各自路径正常读到（起本地 http.server 打一次真请求，核对状态码与字节数）。

## Pitfalls（踩过的坑）

- **⚠️ 去重是单向门：被链起来的两个名字，之后若"本应变得不同"，不先断链就永远修不出来。**
  这是 dedup 的反向失效模式，最容易在"修一个让重复文件变得不重复的 bug"时撞上：
  那批文件之所以重复，正是这个 bug 造成的，于是它们已被链成**同一个 inode**；
  重新生成时往任何一个名字里写，两个一起变、最后一个赢。
  症状极具误导性——**改动明明生效了（多数文件哈希变了），但"成对必须不同"这条判据死活不过**，
  看起来像修复失败，实际是文件系统层面根本写不出两份不同内容。
  ⇒ **重导一批产物之前，先对这批查 `os.stat(p).st_nlink > 1`；有就先断链再生成。**
  断链的安全做法（内容不变、只是各自一份数据）：
  ```python
  tmp = p + '.unlink.tmp'
  with open(p, 'rb') as r, open(tmp, 'wb') as w: w.write(r.read())
  os.replace(tmp, p)          # 该名字拿到新 inode；配对的另一半仍指向旧 inode
  ```
  注意只需对**每对拆一次**即可（拆完另一半的 `nlink` 自然回到 1），别按"看着像对"就全拆。
  代价是磁盘实占回升——这是**正确**的，因为它们本来就不是重复文件。
- **同一理由的反向用法**：任何"逐字节相同"的历史结论，如果那批文件被去重过，
  **不能只比哈希**——哈希相同可能只是因为它们是同一个 inode。比内容之前先看 `st_nlink`。
- **`send2trash` 未安装**：主流程不删文件用不到它；但配套的「回收站兜底删除」若需要，别依赖 `send2trash`，改用 PowerShell `Microsoft.VisualBasic.FileIO.FileSystem::DeleteFile/DeleteItem(..., 'OnlyErrorDialogs', 'SendToRecycleBin')`。
- **PowerShell `-File` 模式类型字面量绑定失败**：`[Microsoft.VisualBasic.FileIO.FileSystem]` 在 `-File` 脚本里于**解析期**就绑定，报「找不到类型」。加 `-NoProfile` 屏蔽用户 profile 干扰，并改用 `powershell -NoProfile -Command '...'`（bash 用**单引号**包裹、`$` 原样传给 PS，规避引号地狱），`-Command` 模式下类型可正常加载。
- **跨卷**：硬链接只能同分区/卷；跨盘会 `OSError`，此时应放弃而非静默 copy（脚本已把失败回退为 copy 并计数，需检查回退数是否 >0）。
- **误把近似重复当重复**：一定做真实字节比对，不能只信 size 或只信 sha256（sha256 命中后再 open+read 逐字节确认）。
- **freed 统计偏低误判为失败**：见第 4 步幂等说明，重跑已链组不重复计属正常。
- **别与软链/快捷方式混**：软链是指针，目标没了就失效；硬链与正常文件几乎无差别，`http.server`/`<img>` 直接当普通文件读，更稳。
- **断链类操作必须"先备份再动手"**：`os.remove` 是不可逆的一步，若后续语句抛异常就会留下缺件/0 字节文件。真实事故：造漂移的测试脚本按 utf-8 读一个 **GBK（`chcp 936`）的 .bat**，`UnicodeDecodeError` 恰好发生在 `os.remove(dst)` 之后 → 运行目录副本被留成 0 字节。**碰 .bat / 中文控制台脚本一律二进制读写**，且动手前把目标目录整份拷进带日期的备份区。
- **失败分支也要真跑**：漂移探测器（`--check`）和"内容不同就拒绝换链"这类保护，只有人为制造一次漂移/哈希不符才算验过；只测成功路径的探测器等于没有探测器。合成一份临时台账/临时文件对来测，比拿真资产练手安全。
- **测 git 钩子用临时索引**：`T=$(mktemp); export GIT_INDEX_FILE=$T; git read-tree HEAD` 之后再 `git add`，收尾 `unset GIT_INDEX_FILE; rm -f $T`——否则自测会把文件塞进真实暂存区，连带提交进别人的改动。
- **⚠️ 同一文件的并行 Edit 会静默丢改动（2026-10-13 实测，一次 UI 轮连丢 4 笔）**：
  同一轮对话里对**同一个文件**并发发多个 Edit，不是全部失败、也不是全部生效——实测形态是
  **第一批的第一笔落盘、第二笔及以后被整笔丢掉，而工具对每一笔都回报 "Successfully edited"**。
  丢的改动不报错、不留痕，只能靠事后 grep 核验才发现（那轮的表现：CSS 变了、HTML 没变，
  页面渲染出一半新一半旧的"分裂态"）。
  ⇒ **规则：同一文件的多次 Edit 必须串行**（一笔落盘确认后再发下一笔）；跨文件的并行才安全。
  收尾必做「grep 标记原子句」核验：给每笔改动挑一个不可能撞车的关键词（类名 / 选择器 / id），
  全部 grep 到才算完。这一条与「Edit 原子保存断硬链」是同一族纪律：
  硬链断不断有 `--check` 兜底，并行丢改动没有任何探测器，只能靠串行 +  grep 自证。

## Verification 清单

1. 方案汇总展示给用户且其确认重复均为真实冗余后才动手。
2. 小样本 apply「0 问题」+ 小样本 HTTP「x/x 全部通过」后才跑全量。
3. 全量 apply「0 问题、0 回退 copy」（有回退要逐条排查跨卷/权限）。
4. 全量 HTTP 校验**所有**受影响路径 200 + 长度 + sha256 全一致。
5. 磁盘实占 logical vs physical 差额 ≈ 预估，抽样 `nlink>1`。
6. **反向闸门**：若本轮要"重新生成一批可能已被链起来的产物"，先证明这批里 `st_nlink>1` 的数量以及它们是否本应变得不同；要变就先断链，再重导。重导后必须验"本该不同的那几对哈希确实不同"——只验"生成了"看不出这个问题。
