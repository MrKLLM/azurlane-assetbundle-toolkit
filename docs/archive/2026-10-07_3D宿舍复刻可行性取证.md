for f in fs:
    d = json.load(open(f, encoding='utf-8'))

### D-1 three.js 侧重写为什么可行：三条路

- **(a) 照参数表重写（推荐主线）**：`m_PropInfo` 给"有哪些旋钮 + 类型 + 默认值"，`m_SavedProperties` 给"当前每个旋钮的值"，`m_ShaderKeywords` / `m_CustomRenderQueue` 给变体与队列，美术侧有参考图。→ 这是**照单施工**，不是猜。
- **(b) 反编译 blob 再对照**：DXBC→HLSL、SPIR-V→GLSL(spirv-cross) 都有工具链，产物脏但语义正确。MuMu 那份 Android 包会是 GLES3/SPIR-V，比这份 PC 包的 DXBC 更好反。**本机未装任何反编译工具**。
- **(c) 光照不靠实时重建**：`dorm3d/scenesres/*.shadowmap` 是烘焙阴影图，`LightmapSettings` / `LightProbes` 对象在 `worldmap3d` 里就存在 ⇒ 当第二套 UV 的烘焙贴图贴上去，比"重算光照"更接近原画面。

真正只剩近似的只有一档：**逐像素一致**——描边的 camera-space 实现细节、URP/后处理链、ShaderVariant 的 keyword 组合。这是"像不像"，不是"在不在"。

## 追加-X 第 2 条定案（16:40）：根因在装配器的**通道类型判定**，不在前端

`read_plain_channel` 把"元素宽 = 2 字节"一律按 **float16** 读。这个假设在 UV 上成立，
在蒙皮两个通道上**都不成立**：BlendWeight 是 **UNorm16**、BlendIndices 是 **uint16**。

| 后果 | 机制 | 实测证据 |
|---|---|---|
| **GLB 里所有骨号都是 0** | 整数 `1` 的位模式按半精度解释是次正规数 ≈ 6e-8，`int()` 归零 | 源包 `neck` 行0 骨号 `(1,0)`，GLB 里 `(0,0,0,0)` |
| **权重出现 NaN / -Inf** | `32767` 按半精度 = `0x7FFF` = **NaN**；`32768` = `0x8000` = **-Inf** | `body` 行0 在文件里是 `[nan,nan,nan,nan]`，源包是 `[0.50001,0.49999,0,0]` |
| **`neck` 恰好是对的** | 它的权重通道是 **4 字节 float**，走另一条分支 | 源包与 GLB 行0 都是 `[0.9,0.1]` |

⇒ 每个顶点都被挂到 0 号骨上，这才是"画面空 / 包围盒失衡"的真因。

### 为什么我两道闸都没拦住（这条比 bug 本身更值钱）

2. 同一道闸对 `hair` 也是绿的——因为装配器把权重**除以自身和**，

   修完实测 5/5 网格 `权重全等 骨号全等`，`exit 0`。
